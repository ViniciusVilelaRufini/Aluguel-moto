# API Volti (`services/api`)

NestJS 10 + Prisma 5 + PostgreSQL 16/PostGIS + Redis 7. Implementa as 188 operações de `packages/contracts/openapi.yaml` e o WebSocket de `packages/contracts/realtime.md` (Socket.IO, namespace `/realtime`).

## Como rodar localmente

```bash
cp .env.example .env                    # na raiz do monorepo
cp .env.example services/api/.env       # o Prisma CLI lê o .env da pasta do pacote
pnpm install
pnpm dev:deps                           # postgres, redis, mosquitto, minio (a API cria os buckets ao subir)
pnpm --filter api prisma migrate deploy # aplica prisma/migrations
pnpm --filter api prisma db seed        # São Paulo: 60 motos (Urbana/Sport/Touring), zonas, preços, estações, baterias, usuários dev
pnpm --filter api dev                   # prisma generate + tsc e sobe em http://localhost:3000
```

Ou tudo em containers: `docker compose up -d --build api` (sobe sem `.env`, com padrões de dev; porta do host em `API_PORT`, padrão 3000) (o container aplica as migrações com `RUN_MIGRATIONS=true`; `RUN_SEED=true` roda o seed).

> **Migrações:** aplique com `migrate deploy`. Use `migrate dev` só para criar migração nova, revisando o SQL gerado. A migração inicial tem índices GIST e parciais e `CHECK` escritos à mão, e o setup do e2e confere que existem. Para checar drift, rode `prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script`: o resultado deve ser uma migração vazia.

> `tsx`/esbuild não emite metadados de decorators; por isso o `dev` usa `tsc`. O seed roda com `tsx` (não usa DI).

### Tokens de desenvolvimento (`AUTH_MODE=dev`)

```bash
curl -X POST localhost:3000/dev/token -H 'content-type: application/json' \
  -d '{"sub":"dev-cliente-aprovado","email":"cliente.aprovado@volti.dev","groups":[],"pool":"customer"}'
curl -X POST localhost:3000/dev/token -H 'content-type: application/json' \
  -d '{"sub":"dev-admin","email":"admin@volti.dev","groups":["admin"],"pool":"staff"}'
```

As motos `VLT-0001`…`VLT-0006` ficam dentro das zonas de devolução. O seed do contrato v2 (`prisma/seed-v2.ts`) acrescenta o catálogo de exemplo (`prisma/seed-catalog.ts`): Volti Urbana — urbana com cesto (79/min), Volti Sport — esportiva compacta de 2 lugares (89/min) e Volti Touring — touring com baú (99/min), todos autopropelidos de até 1000 W e 32 km/h, com descrição curta e desbloqueio do plano; as fotos de exemplo (de terceiros, só dev — nunca no git) são baixadas no seed direto para `catalogo/catalog/<slug>.<ext>` no MinIO (só HTTPS e host público em cada salto, até 3 redirecionamentos, até 5 MB, assinatura JPEG/PNG/WebP conferida), e sem rede o modelo fica sem foto (o app mostra o ícone); as motos alternam os modelos pelo código (`VLT-0001` Urbana, `VLT-0002` Sport, `VLT-0003` Touring…), então o lote do galpão tem 6/7/7; 5 estações de troca, odômetro/horas e revisões variadas (em dia, próxima, vencida), uma bateria por moto, 6 baterias na van do `dev-campo`, o cupom `BEMVINDO10` e, para o `dev-cliente-aprovado`, chave Pix (e-mail) e código de indicação `APROVADO7K`. O seed do galpão (`prisma/seed-depot.ts`, idempotente) cria o "Galpão Volti — Pinheiros" (Rua dos Pinheiros, 870; seg–sex 07:00–20:00, sáb 08:00–18:00, dom fechado) e vincula a ele só o lote `VLT-0011`…`VLT-0030` (`DEPOT_CODES`, sem as motos que os e2e usam no fluxo de rua), quando livres, nas coordenadas do galpão; motos fora do lote que apontem para o galpão são desvinculadas e voltam às coordenadas do seed (um banco semeado antes do fix se repara rodando o seed de novo).

## Estrutura

- `src/ports/` — interfaces fixas: `IotGateway`, `RentalBillingPort`, `InsurancePort` (plano mestre), `ObjectStorage`, `QueueBus`, `KycProvider`, `PushNotifier`, `AuthVerifier`, `StaffDirectory` e `CustomerIdentityDirectory` (Cognito; local = no-op), `ReverseGeocoder` (contrato v2: endereço da moto).
- `src/adapters/` — implementações local/aws escolhidas por variável (`AUTH_MODE`, `STORAGE_MODE`, `QUEUE_MODE`, `KYC_PROVIDER`, `PUSH_MODE`). Valor desconhecido em qualquer `*_MODE` recusa subir.
- `src/modules/iot` — **Task 4** (ver "IoT" abaixo).
- `src/modules/payments`, `insurance`, `wallet` — **Task 5** (`docs/pagamentos.md`): `RentalBillingService` (caução por pré-autorização ou Pix, liquidação com captura parcial, inadimplência) sobre `PaymentProvider` (`PAYMENT_PROVIDER=fake|mercadopago`), webhooks do Mercado Pago validados, enfileirados e deduplicados (`ProcessedWebhook`), carteira em ledger somente inserção, `InsuranceService` com `MockInsuranceProvider` e repasse, recibo em PDF no bucket de relatórios e NFS-e (`MockInvoiceIssuer`). No fake, o cartão precisa ser cadastrado antes de alugar (`POST /payments/cards` com `cardToken: tok_visa_4242`); o Pix se confirma sozinho após `FAKE_PIX_AUTOCONFIRM_SECONDS`. O fake guarda tudo em memória: depois de reiniciar a API, cartão (`fake-card-<uuid>`), token (`fake-tok-<uuid>`) e pré-autorização (`fake-pay-<uuid>`) emitidos antes são reidratados como válidos (cartão aprovado; pré-autorização `authorized` que captura o valor pedido), com log `fake_payment_rehydrated`; ids em outro formato e cartões excluídos continuam "não encontrados".
- `src/common/` — enums compartilhados, erros RFC 7807 (`ProblemException` → `type: https://api.volti.com.br/problems/<slug>`), idempotência (`@Idempotent`), paginação por cursor, logger JSON sem dados pessoais.
- Eventos internos: `src/common/events.ts` (os do plano mestre + os próprios da API, ver `docs/decisoes.md`).
- Jobs (`JOBS_ENABLED`): expiração de reservas (TTL do Redis + varredura), retentativa de encerramento `ending`, `rental.updated` a cada 30 s, "você está bem?" (60 s), limpeza diária de `TrackPoint` expirado e, desde a auditoria run-4, expurgo diário (`housekeeping-ttl`, 04:15) de `IdempotencyRecord` vencido e `ProcessedWebhook` com mais de 90 dias (`src/modules/housekeeping/`, lotes de 5000).

## IoT (`src/modules/iot`, Task 4)

| Variável | Valores | Efeito |
|---|---|---|
| `IOT_MODE` | `local` (padrão), `aws`, `stub` | `LocalMqttIotGateway` (Mosquitto em `MQTT_URL`, com o servidor emulando o serviço de shadow), `AwsIotGateway` (IoT Data Plane em `IOT_ENDPOINT`; telemetria pela fila SQS `telemetria`) ou o `StubIotGateway` (confirma na hora; padrão dos e2e do fluxo de aluguel) |
| `GEOFENCE_MODE` | `local` (padrão), `aws` | ENTER/EXIT pelo PostGIS; `aws` também sincroniza a geofence collection e o tracker do Amazon Location (`LOCATION_GEOFENCE_COLLECTION`, `LOCATION_TRACKER_NAME`) |
| `IOT_CONFIRM_WAIT_MS` | `3000` | quanto a chamada de comando espera o `reported` antes de responder `in_progress` |
| `IOT_COMMAND_TIMEOUT_MS` | `30000` | sem `reported` → `failed`/`timeout` (o lock tem 120 s) |
| `IOT_OFFLINE_AFTER_MS` | `180000` | sem notícia → `iot.connectivity` offline |
| `IOT_RECONNECT_GRACE_MS` | `10000` | depois de qualquer reconexão, nenhuma amostra de velocidade (telemetria, reported, polling do shadow) vale para travar neste intervalo (fila offline do MQTT esvaziada). Reconexão = presença `connected` (só `local`), primeira mensagem depois de offline, primeira amostra do processo ou lacuna (`IOT_RECONNECT_GAP_MS`) |
| `IOT_QUEUE_LAG_MS` | `5000` | telemetria com atraso de fila `(chegada − chegada anterior) − (timestamp − timestamp anterior)` maior que isto saiu da fila offline → reconexão (a amostra cai na graça); independe da cadência e do desvio do relógio do rastreador |
| `IOT_RECONNECT_GAP_MS` | `15000` | lacuna entre mensagens do rastreador (qualquer canal, hora de chegada) que conta como reconexão, nos dois modos; com a moto parada/travada vale `max(isto, 150000)`. No `aws` é o único detector de quedas mais curtas que `IOT_OFFLINE_AFTER_MS` (a presença vai para o EventBridge) |
| `OUT_OF_AREA_LOCK_MINUTES` | `5` | bloqueio seguro depois de sair da área de operação |
| `TRACK_RETENTION_DAYS` | `90` | `TrackPoint.expiresAt` |

**Rastreadores só relé (`Tracker.controlMode = relay_only`, GT06 via Traccar).** O `CommandsService` lê o tipo do rastreador e o
passa ao gateway (`CommandRequest.controlMode`). `lock` usa o `RelayLockService` (estado no Redis, `iot:relay-lock:*`): sem rampa,
espera 3 telemetrias aceitas < 3 km/h cobrindo ≥ 20 s, no máximo 12 s entre duas seguidas (`RELAY_STILL_MIN_SAMPLES`,
`RELAY_STILL_MIN_SPAN_MS`, `RELAY_MAX_SAMPLE_GAP_MS`; a última fresca, ≤ 10 s) e grava `travada: true` uma vez — regra da
bancada do J16 (TIMER mínimo de 10 s; `docs/decisoes.md`, 2026-11-03); 120 s sem parar → `did_not_stop` sem corte;
corte sem confirmação em 120 s → `timeout` e o corte pendente apagado (`travada: null`; nunca `travada: false`, que soltaria
uma moto cortada cujo status só atrasou). `speed_limit` e `horn` → `unsupported_by_tracker`. O fluxo
`speed_control` (`SafeLockService`) não muda. Spec: `docs/superpowers/specs/2026-10-27-volti-rastreador-gt06-relay-only.md`.
Moto que cai durante a espera: o comando volta de `in_progress` para `pending`/`offline` (única regressão aceita pelo
`CommandsService`, só pelo `iot.command-updated`); na reconexão a janela de 120 s recomeça e o comando volta a `in_progress`.
Moto já travada (`LiveStateStore.lockConfirmed`: online e `locked` gravado por telemetria/reported depois da reconexão — campo
`lockedAt` e `reconnectAt` no hash `iot:live:*`, compartilhados entre as instâncias — o `reconnectAt` só por máximo atômico (`hsetMax`), nunca regride; o estado em branco de uma presença sem mensagem não conta) → `lock` confirma sem gravar nada; a
espera retomada e o prazo da trava também terminam `confirmed` (nunca `travada: false`) se a moto já estiver travada.
Só vale origem **depois da graça** da reconexão (`IOT_RECONNECT_GRACE_MS`): o `reported` do tick da reconexão (memória da ponte) e
a fila offline com relógio adiantado nunca confirmam; um `reported.travada = true` só confirma por esse mesmo critério (com o
corte enviado, também precisa ser posterior a ele). As varreduras releem o estado ao vivo do Redis antes de decidir. Ao começar, o lock `relay_only` apaga
(`desired.travada = null`) um `travada` pendente no shadow (ex.: `false` de um unlock que a moto offline não recebeu), para a
ponte não reaplicar `engineResume` na reconexão; nunca grava `travada: true` fora do corte.
Unlock `relay_only` confirma **só** por `reported.travada: false` com hora depois do `releaseAt` (gravado antes de publicar o
`travada: false`) e sem `reported.travada: true` depois dele (`LiveStateStore.unlockConfirmed`; campos `reportedFreeAt`/
`reportedCutAt` do hash `iot:live:*`, só por máximo atômico `hsetMax`). No modo aws o `false` do polling (metadata em segundos)
fica em `reportedFreePollAt` e é comparado com o release truncado ao segundo. Nunca pelo `locked` do estado: a telemetria da ponte
sai com `travada: false` quando o bit de corte está velho ou desconhecido (A4-6). Prazo do unlock `relay_only`: **90 s**
(`RELAY_UNLOCK_TIMEOUT_MS`; `GatewayOptions.relayUnlockTimeoutMs`), para cobrir o heartbeat de 60 s do J16 — o normal é confirmar
pela resposta do J16 ao comando (~1 s); expirar só reporta `failed`/`timeout`, nada é gravado. O início do aluguel continua
esperando `IOT_COMMAND_TIMEOUT_MS` + 5 s (limite do aceite da entrega, `IDEMPOTENCY_STALE_MS`). `speed_control` não muda.

**Estado do rastreador no banco e `vehicle.state` (bancada do J16, 2026-11-03).** `VehiclesService.syncTrackerState`: `Vehicle.locked`
e `Vehicle.batteryKnown` vão para o Postgres na hora em que mudam (escrita condicional, vale entre instâncias) e `lastSeenAt`
(hora do servidor em que o rastreador foi ouvido) no máximo a cada 15 s (`LAST_SEEN_WRITE_INTERVAL_MS`) — pela telemetria e
também pelo `reported` (status/heartbeat da ponte, evento interno `iot.reported`; o polling do shadow grava só a trava, não é
sinal de vida). Alguma escrita pegou, ou a conectividade mudou → WS `vehicle.state` na sala `fleet`
(`{ vehicleId, locked, online, lastSeenAt, batteryKnown, ts }`, `packages/contracts/realtime.md`). A gravação de 30 s da telemetria
não grava mais `lastSeenAt`, e a queda (offline) não o avança. Telemetria com `bateria_conhecida: false` → `batteryKnown = false`,
`batteryPct` 0 e a carga da bateria instalada não muda; o mapper expõe `batteryKnown` (ausente no banco antigo = `true`) e,
sem leitura, `batteryPct`/`estimatedRangeKm` 0. `firmwareVersion` vem do `Tracker` vinculado (fallback: a coluna da moto).
O overlay do Redis (`vehicles/live-overlay.ts`) sobrepõe trava (só com `lockedAt` conhecido), `online`, `lastSeenAt` e bateria
conhecida mesmo sem posição no Redis, e aceita o `lastSeenAt` do banco até 10 min à frente (relógio do rastreador adiantado).
Sem cache por instância: toda mensagem faz a escrita condicional. A trava do rastreador (`reported`, resposta ao comando, comando confirmado) vence a da telemetria por 90 s (`REPORTED_LOCK_PRECEDENCE_MS`; colunas `lockedAt`/`lockedFromReport`), porque a telemetria da ponte sai `travada: false` com o bit velho; `vehicle.state.ts` é a hora da fonte. `positionAt` (banco e hash `iot:live:*`) é a hora da medição da posição — o link de localização usa ela, não o `lastSeenAt`. `vehicle.position` e `VehicleSummary` levam `batteryKnown`; a troca de bateria na tarefa não grava carga da retirada sem leitura. Migrações `20261103140000_vehicle_battery_known` e `20261103150000_vehicle_tracker_provenance`.
Ordem das amostras (Task 11b): um `reported.velocidade_kmh` parado (< 3 km/h) é datado pela chegada e **não** vira barreira de
ordem para a telemetria (datada pelo `fixTime`); com o GPS mais atrasado que a cadência (ex.: GPRS com buffer), senão toda
telemetria seguinte seria "velha" e a parada nunca se confirmaria. `reported` em movimento (≥ 3 ou inválido) continua barreira, e
qualquer `reported` em movimento continua zerando a sequência parada.
O invariante (corte só com parada confirmada, fora da graça, antes do prazo, uma vez por trava) tem teste de propriedade

Sem `deposit` → caução de balcão de valor 0 com o método do pagamento. Chama `RentalStartService.start(atendente, …, 'counter:<id>', { fromHandover, counter })`: o cliente é o da reserva, o atendente é o ator do `unlock` (auditoria), mas o comando sai com autoridade de cliente (`DispatchInput.authority: 'customer'`): trava da equipe/sistema ou modo roubada recusam o unlock (`locked_by_staff` → `409 vehicle-unavailable`, nada gravado); sem `holdDeposit`, cupom nem assinatura; o snapshot é o `counterSnapshot`. Depois do desbloqueio confirmado, na transação que cria o aluguel: `Deposit` de balcão `held` (`counter-deposit:<id>`), `Payment` `rental` `paid` (`counter-checkout:<id>`, `recordedById` = atendente; vira o `Rental.paymentId`), `Payment` `deposit` `paid` só com caução > 0 (`counter-deposit-payment:<id>`), entrega `accepted` com `contractPhotoKeys`, `prepaidUntil` = `startedAt` + período e evento `started` com ator `staff`. Desbloqueio não confirmado → nada é gravado (a compensação existente devolve a moto a `reserved`, trava de novo e cancela a apólice). Reserva antiga (beta12) com caução de gateway retida → pedido de liberação depois do commit. Erros do início: `403 location-consent-required` → `422` "Peça ao cliente para permitir a localização no app."; os demais como no aceite (`acceptError`); falha de negócio grava `lastError` na entrega. Sucesso: AuditLog `rental.counter_checkout` (ids, plano, quantidade, método, valor, caução; sem dado pessoal), `handover.updated` `accepted` e repasse do prêmio à seguradora (falha só loga).

Fechamento do balcão e débito em aberto (Task 6 do mesmo plano): com `snapshot.counter`, `RentalEndService.doFinalize` calcula sem carteira nem pacote (`walletAvailableCents: 0`, `minutesAvailable: 0`, nenhum lançamento na carteira) e **nunca chama o gateway** (`billing.settle`): na mesma transação que fecha o aluguel, `recordCounterClose` (`payments/counter-close.ts`) grava o resíduo (`totalCents`, já descontado o pré-pago) como `Payment` `rental` `pending` com o método do pagamento pré-pago (`counter-excess:<rentalId>`, sem `depositId`; repetição reaproveita pela chave) e o torna o `Rental.paymentId`; sem resíduo, o `paymentId` continua o pré-pago. Caução de balcão de valor 0 ainda `held` vira `released`. Aluguel do balcão sem pré-pago de balcão (inconsistência) fecha mesmo assim: o excedente usa o método da caução de balcão (ou `cash`), log `counter_close_prepaid_missing` e alerta `payment_needs_review` high ("Aluguel do balcão fechado sem pré-pago consistente — revisar acerto"). `retryEnding` trata cada aluguel no seu try/catch (log `rental_end_retry_item_failed`): um erro não derruba o lote. Dívida em aberto (`open-debt.ts`): `openDebtWhere`/`isOpenDebt` = `failed` de aluguel/assinatura **ou** `counterDebtWhere` (`rental` `pending` com método de balcão e sem `debtSettledAt`); `hasCounterDebt`; a exclusão de conta conta como liquidação em curso só os `rental` `pending` fora do balcão (o débito do balcão já entra pela dívida). Saldo (`DelinquencyService.outstandingMap`) = valor − carteira − caução capturada (só fora do balcão) − Σ `debt_settlement` `paid` do débito. `POST /payments/{id}/retry` de débito de balcão → `409 debt-not-payable` "Este valor é acertado no galpão.". Jobs do gateway ignoram o balcão: órfãos de `retryPendingSettlements` filtram `method notIn` balcão, `settleUnbilledRentals` pula aluguel com `prepaidUntil`, e `onReleaseRequested`/`releaseDeposit` não mexem em caução de balcão (log `deposit_release_counter_ignored`; a devolução é no galpão).

Acerto no balcão (Task 7 do mesmo plano): `CounterSettlementService` (`payments/counter-settlement.service.ts`), sem gateway. `GET /rentals/{id}/counter-balance` (`admin`, `operacao`, `campo`, `financeiro`) devolve as dívidas em aberto do cliente do aluguel com saldo > 0 (`openDebtWhere` + `outstandingMap`), as cauções de balcão `held` com disponível > 0 (`amountCents − capturedCents − refundedCents`) que não sejam de aluguel ainda aberto (`active`/`paused`/`ending`), só o primeiro nome e `debtTotalCents`. `POST /payments/{id}/counter-settle` (`admin`, `operacao`, `campo`, `Idempotency-Key`) quita total ou parcialmente: exatamente um entre `method` e `fromDepositId` (`400`); trava o débito (`SELECT ... FOR UPDATE`) e relê o saldo na transação; não é dívida em aberto → `409 debt-not-payable`; débito de assinatura ainda em cobrança automática (`past_due`) → `409 debt-in-collection` (débito de aluguel `failed` sempre quita); `fromDepositId` de caução de aluguel ainda aberto → `409 conflict` ("A caução só abate dívidas depois do encerramento do aluguel."); acima do saldo ou do disponível da caução (travada também) → `422 counter-amount-mismatch`. Cada parte vira `debt_settlement` `paid` (`settlesPaymentId`, `recordedById`, `reference`, `depositId` quando abate a caução, que soma `capturedCents` e vira `captured` ao zerar). Saldo 0 → `debtSettledAt`, `debtSettlement: payment` e, no débito de balcão `pending`, `paid`; depois `clearDelinquencyIfSettled`. `POST /payments/deposits/{id}/counter-refund` devolve a caução do balcão só com o aluguel encerrado (`409`), trava a caução, soma `refundedCents` (≤ disponível, senão `422`) e, ao zerar, deixa `captured` (houve abatimento) ou `released`. AuditLog `payment.counter_settle` / `deposit.counter_refund`. Débito quitado manualmente (`clearManually`: `debtSettledAt` com status `pending`) não é mais dívida: fica fora do saldo e o `counter-settle` responde `409`.

LGPD e aviso do período (Task 8 do mesmo plano): o export (`GET /lgpd/export`) traz `contractPhotoKeys` de cada entrega; a exclusão da conta apaga as fotos do contrato junto com as da vistoria (mesmo bucket `returnPhotos`) e zera `contractPhotoKeys`/`photoKeys` na anonimização. Caução de balcão `held` com disponível > 0 bloqueia a exclusão (`409 account-deletion-blocked`, "Retire sua caução no galpão antes de excluir a conta."); o débito de balcão em aberto já bloqueia pela regra de dívida (`open-debt.ts`). Job `counter-period-remind` (`rentals/counter-period-reminder.service.ts`, `@Interval` 60 s, `ExclusiveJob`, respeita `JOBS_ENABLED`): aluguéis abertos com `prepaidUntil` na próxima hora e `prepaidReminderSentAt` nulo recebem um push ("Fim do período" — "Seu período termina às HH:MM. O excedente é acertado no galpão.", horário de São Paulo, `data.type: rental.prepaid_ending`); o claim condicional grava `prepaidReminderSentAt` antes do envio (no máximo uma vez; falha do push só loga).

Chegada no galpão e origem da trava: o lock da chegada (`purpose: rental_depot_return`, ator de sistema) é uma trava de **estacionar**, como `rental_end`/`rental_force_end`/`rental_start_rollback` (`PARKING_LOCK_PURPOSES` em `commands/commands.service.ts`): não grava `iot:lock-origin` `system`. Antes ele gravava, e com o gateway real o fechamento via `isLockedByStaff` mandava a moto para `maintenance` com alerta e o próximo `counter-checkout` recusava a moto (`409 vehicle-unavailable`). O `IOT_MODE=stub` dos e2e não implementa `lockedByStaff`, por isso o e2e não pegava; a regra está coberta em `commands.service.spec.ts`.

Fix round 2: assinatura `canceled`/`expired` nunca reabre. A cobrança tardia é estornada pelo gateway (`PaymentRefund`, chave `subscription-late-refund:<paymentId>`). O cancelamento no gateway de assinatura expirada ou de conta excluída fica pendente (`gatewayCancelPendingAt`) e é refeito pelo job `subscriptions-gateway-cancel-retry` (5 min). O odômetro usa compare-and-set atômico no Redis (`RedisStore.hcas`, testado contra o Redis real em `test/usage-tracker-redis.e2e-spec.ts`).

## Troca de bateria na estação via QR (`src/modules/station-swaps`, spec `2026-10-22-volti-troca-bateria-qr`)

Cliente com aluguel em andamento escaneia o QR fixo da estação e troca a bateria sozinho. `POST /swap-stations/{id}/swaps` (cliente, `Idempotency-Key` obrigatória) valida, nesta ordem: QR (`404 station-not-found`), aluguel do próprio cliente `active`/`paused` (`409 rental-not-active`), uma troca aberta por aluguel (`409 swap-open`, também pelo índice parcial `StationSwap_one_open_per_rental`), estação ativa, aberta (`open24h` ou `openingHours` interpretável no fuso de São Paulo; texto ilegível libera) e com carregada livre (`availableBatteries` menos as trocas em andamento) (`422 station-unavailable`), celular a ≤ 50 m (`422 too-far`) e moto parada — mesma regra do bloqueio seguro: velocidade 0 fresca, moto travada e online ou aluguel pausado; desconhecida = em movimento (`422 vehicle-moving`; `IotGateway.knownSpeedKmh`). `GET /swap-stations/{id}/swaps/{swapId}` (dono + `admin`/`operacao`/`suporte`), `POST .../cancel` (dono, só em `opening_slot`/`awaiting_return`; depois `422 swap-not-cancelable`), `GET /swap-stations/{id}/swaps` (staff, cursor, filtro `status`, com `customerId` e `distanceM`).

- **Estados:** `opening_slot` → `awaiting_return` (`slot_opened`) → `returned` (`battery_returned`) → `releasing` (`slot_closed`; só aqui a API manda `release_battery`) → `completed` (`battery_released`). Vaga fechada sem devolução → `canceled`. Eventos repetidos/fora de ordem/de outra estação são ignorados. Eventos, cancelamento e prazo de uma troca passam por uma fila por troca (um de cada vez, CAS no status). WebSocket `station_swap.updated { swapId, status }` na sala `customer:{id}`.
- **Última bateria (fix 1, C1):** a checagem de estoque e a inserção correm na mesma transação com `SELECT … FOR UPDATE` na estação; contam as trocas em andamento e as `failed/release_timeout` dos últimos 30 min (a estação ainda pode liberar atrasada). Duas requisições pela última carregada → `201` + `422 station-unavailable`.
- **Moto parada (fix 1, I3):** velocidade 0 fresca ou moto travada e online — o aluguel `paused` sozinho não basta (pausado com velocidade desconhecida → `422 vehicle-moving`).
- **Prazos:** 3 min por etapa (`expiresAt`, `STATION_SWAP_STEP_TIMEOUT_MS`); job `station-swap-timeouts` (15 s, `JOBS_ENABLED`): sem resposta da estação → `failed/station_timeout`; sem devolução → `canceled/return_timeout`; devolvida sem liberar → `failed/release_timeout` + alerta `command_failed` (alta) para a operação. Liberação atrasada depois desse prazo ainda completa a troca (o cliente recebeu a bateria).
- **Aviso à estação (fix 1, I2):** cancelamento pelo cliente e todo prazo vencido mandam `abort_swap { swapId, slotNumber? }`; a estação fecha a vaga e confirma com `slot_closed` (ignorado pela API numa troca encerrada). Devolução que chega depois de `canceled_by_customer`, `return_timeout` ou `station_timeout` vale como devolução: a bateria entra no estoque, a troca volta para `releasing` (com a estação travada, mesma conta da criação) e a estação libera uma carregada; sem carregada → `failed/no_battery_after_return` + alerta.
- **Devolução atrasada com o aluguel fechado (fix 2, I-1/M-4):** antes de voltar a `releasing`, a transação trava a estação e o aluguel (`FOR UPDATE`, sempre nessa ordem) e confere aluguel `active`/`paused` e nenhuma outra troca aberta; se falhar, a devolução fica registrada e a troca vira `failed/return_after_close` + alerta (nunca P2002: um P2002 inesperado cai numa transação nova que grava o mesmo resultado, para o evento não virar mensagem envenenada no grupo FIFO). Devolução numa troca encerrada por outro motivo só entra no estoque + alerta.
- **Encerramento pelo staff (fix 2, M-2):** encerramento forçado e chegada no galpão fecham as trocas abertas sem devolução (`canceled/rental_force_ended` + `abort_swap`); com a devolução registrada a liberação termina, mas `Vehicle.batterySerial` e o registro da bateria não mudam com o aluguel já fechado (alerta para conferir).
- **Criação × encerramento (fix 2, M-3):** a criação relê o status do aluguel e a troca aberta com a linha do aluguel travada (depois do lock da estação); o encerramento pelo cliente trava a mesma linha antes de conferir a troca aberta e passar a `ending`.
- **Série divergente (fix 1, M1):** bateria devolvida ou liberada que consta `in_vehicle` em outra moto nunca é desvinculada: troca `failed/serial_mismatch` + alerta. Devolvida diferente da registrada na moto → alerta (só ids), a troca segue.
- **Custódia (2026-10-26, Task 8.3):** só sai bateria `in_station` desta estação (lida e conferida no `where` do `updateMany`); liberada de outra estação, van, galpão, com defeito, baixada ou sem cadastro → `failed/serial_mismatch` + alerta, nada gravado. O alerta traz a série (a moto pode estar com ela sem registro). O seed alinha as carregadas cadastradas de cada estação ao `availableBatteries` (`prisma/seed-stations.ts`, idempotente); o stub (`IOT_MODE=stub`) só libera a `serialHint` e, sem ela, deixa a troca vencer pelo prazo. Devolvida `defective`/`retired` mantém o status (fica na estação, não vira `charging` nem conta como disponível) + alerta `station_return_out_of_service`.
- **Aluguel durante a troca (fix 1, I1/I7):** `GET /rentals/current` traz `currentStationSwap` (troca aberta, visão do cliente). Com troca aberta, `POST /rentals/{id}/end` e `POST /rentals/{id}/swap` → `409 swap-open`; o encerramento forçado pelo staff continua permitido.
- **Estoque:** devolvida → `Battery` `charging` na estação com série e carga lidas (uma vez por troca); liberada → `availableBatteries − 1` (nunca negativo), bateria `in_vehicle` na moto com +1 ciclo (mesma regra da troca do operador), `Vehicle.batterySerial`/`batteryPct` atualizados. A API sugere a carregada (`serialHint`: `in_station`, ≥ 90 %, mais carregada) e grava a que a estação informar.
- **Taxa:** congelada na criação (`feeCents`): 0 nos planos `day`/`weekly`/`monthly`; nos `minute`/`hour`, a taxa de sistema `battery_swap_fee` (padrão 500, criada pela migração; o admin edita em `PUT /pricing/fees/{id}`, não apaga). Cobrada só no fechamento: `RentalEndService` soma uma linha `battery_swap_fee` por troca `completed` com taxa na mesma liquidação.
- **LGPD/logs:** a posição do celular só é usada na validação; a troca guarda a distância (só staff vê). Logs só com ids. O export LGPD traz `stationSwaps`.
- **Thing da estação (Task 12 das lacunas):** `SwapStation.thingName` (único, `station-<uuid>`; a criação pelo painel grava `station-{id}` quando não informada; nulo nas linhas antigas = `station-{id}`). Os comandos vão para a thing do cadastro e os eventos são atribuídos à estação com esse `thingName` (ou, sem nenhuma, à `station-{id}` cujo cadastro não aponta para outro armário); thing desconhecida → evento ignorado (log `station_event_unknown_thing`). A criação de troca relê `active` sob o lock da estação, então uma desativação pelo painel nunca deixa nascer troca numa estação inativa; eventos de trocas já em curso (inclusive devolução atrasada) continuam sendo processados numa estação inativa.
- **Porta da estação** (`src/ports/station-gateway.port.ts`), pelo mesmo `IOT_MODE`: `stub` (`StubStationGateway`, avança sozinha a cada `STATION_STUB_STEP_MS`, padrão 1500 ms; `setAuto(false)` e `emit` nos testes; **recusado em produção**: com `NODE_ENV=production`, `IOT_MODE=stub` não sobe), `local` (`MqttStationGateway`, Mosquitto + `services/station-sim`) e `aws` (`AwsStationGateway`: `Publish` no IoT Data Plane; eventos da fila SQS `estacoes`, `SQS_QUEUE_ESTACOES_URL`). Tópicos `estacoes/station-{id}/comandos|eventos`.
- **Modo aws — fila FIFO (fix 1, I4):** `SQS_QUEUE_ESTACOES_URL` tem de terminar em `.fifo` (`MessageGroupId` = `thing` da estação); com outra fila (ou sem ela) a API não sobe. O `SqsQueueBus` lê o `MessageGroupId` e, quando o handler de uma mensagem falha, não processa nem apaga o resto do mesmo grupo naquele lote (as mensagens voltam na ordem depois do visibility timeout); os outros grupos seguem.
- **QR da estação:** `SwapStation.stationCode` = `vst1.<id>.<HMAC-SHA256 truncado, base64url>` assinado com `STATION_QR_SECRET` (obrigatório em produção; em dev, segredo local). A API confere a assinatura **e** a igualdade com o banco. O código nunca sai em `SwapStation`. **Emissão (fix 1, I6), fora do seed:** script de operação `pnpm --filter api stations:qr` (emite para as estações sem código; `--reissue` regrava todos com o segredo atual — revogação depois de trocar o `STATION_QR_SECRET`; `--station=<id>` filtra). Em produção: `node dist/cli/issue-station-qr.js [--reissue]` numa task avulsa do ECS com `DATABASE_URL` e `STATION_QR_SECRET`. Admin e operação leem o QR de uma estação em `GET /swap-stations/{id}/qr` (o mesmo código do script; emite na hora se faltar; AuditLog `swap_station.qr_read`, sem o código) — o painel desenha e imprime o QR a partir dele.

## Ciclo de vida das baterias no galpão (`src/modules/batteries`, `docs/decisoes.md` 2026-10-24)

Status: `in_vehicle`, `in_van`, `charging` (no galpão `depotId`, ou na estação `stationId` depois da troca por QR), `charged` (carregada e pronta no galpão, carga 100 até sair), `in_station`, `defective` (fora de uso) e `retired` (baixa).

| Rota | Grupos | Regra |
|---|---|---|
| `POST /batteries` | admin, operacao | cadastra por série no galpão ativo, `charging` (carga informada, padrão 0) ou `charged` (100); série duplicada → `409`; galpão inexistente → `404`, inativo → `422 depot-inactive` |
| `POST /batteries/{id}/mark-charged` | admin, operacao, campo | `charging → charged` (carga 100, mesmo galpão); carregando numa estação (sem galpão) → `in_station` e `availableBatteries + 1`; outro status → `409` |
| `POST /batteries/{id}/report-defect` | admin, operacao, campo | `{ reason }`; de `charging`/`charged`/`in_van`/`in_station` → `defective`; instalada numa moto → `409` (retire antes). Na estação, carregada sai do `availableBatteries`; na van, `holderId` é mantido (quem está com ela) e ela some do estoque da van |
| `POST /batteries/{id}/retire` | admin, operacao | `{ reason? }`; de `defective`/`charging`/`charged` → `retired` (limpa galpão, van e estação) |
| `GET /batteries/{id}/movements` | admin, operacao, suporte, campo | cursor, mais recente primeiro |
| `GET /batteries?depotId=&status=` | admin, operacao, campo | `statusCounts` com os 7 status (filtros `depotId`/`holderId`/`q`, sem `status` nem paginação); campo com `holderId` de outra pessoa → `403` |

- **Van:** `load` recusa `defective`/`retired` (`409`), bateria na van de outro operador (`409 battery-in-other-van`) e, para o grupo `campo`, bateria de estação (`409 battery-at-station`; `admin`/`operacao` podem), tira a bateria do galpão (`depotId` nulo) e mantém a carga conhecida (`chargePct` só na criação); séries que ainda estavam `charging` voltam em `loadedChargingSerials`. `unload` sem `stationId` grava `charging` com o `depotId` do corpo, ou do único galpão ativo; com mais de um (ou nenhum) → `422 depot-required`.
- **Movimentações (`BatteryMovement`):** uma linha por transição, na mesma transação — cadastro (`fromStatus` nulo), van (carregar/descarregar no galpão ou na estação), mark-charged, defeito, baixa, troca na tarefa de campo (retirada → van, instalada → moto, outra registrada na moto → `charging`) e troca na estação por QR (devolvida → `charging` na estação, liberada → moto; ator = cliente). Galpão/estação/moto da linha: o destino, senão a origem. A troca na tarefa também recusa instalar, ou registrar como retirada, bateria `defective`/`retired` (`409`). Custódia (2026-10-26): uma troca por tarefa `battery_swap` (`409 task-type-mismatch`, `409 battery-swap-already-recorded`); a instalada sai da van de quem registra ou é nova (`409 battery-not-in-van`, também se constar numa moto); série nova cadastrada ao mesmo tempo (P2002) → `409 conflict`; a retirada é a bateria da moto e nenhuma série de outra moto é reatribuída (`409 battery-serial-mismatch`); `installedBatteryPct` só para bateria nova.

## Fechamento sem cartão (R2-01, lacunas Task 16)

- Ordem no fechamento: **carteira → caução → cartão salvo → dívida**. A carteira é debitada (`rental_charge`) na transação que fecha o aluguel (cliente travado com `FOR UPDATE`), aparece como linha `wallet` no `breakdown` e só o restante vai para a liquidação; carteira cobrindo tudo → pagamento `method: wallet` e caução liberada. A caução Pix abate e devolve só o saldo; sem cartão, o restante vira dívida (`outstandingCents`), paga no app por Pix (`POST /payments/{id}/retry`).
- O `Payment` do aluguel registra o bruto, com a parte da carteira em `walletCents` (NFS-e e PDF pelo bruto); o estorno devolve primeiro a parte do gateway e depois credita a carteira (`refund` no ledger).
- Dívida em aberto (ou flag `delinquent`) → reservas recusadas com `409 payment-pending` ("Pague o valor pendente para alugar de novo."); `POST /rentals` segue `403 customer-delinquent`.
- `GET /rentals/{id}/receipt`: `paymentStatus` (`paid`/`pending`/`processing`), `paymentId`, `depositUsedCents`, `depositReleasedCents`, `amountDueCents`; `pdfUrl` só pago. Quitada a dívida (Pix, cartão, webhook tardio ou manual), o recibo (PDF + NFS-e) é emitido.

## Várias instâncias e integrações (lacunas T5, `docs/decisoes.md` 2026-10-24)

Com rampa ativa, só reduções. Redis fora: lock usa rampa local em memória, migrada para o Redis quando ele volta.

## Auditoria run-4 — suporte e KYC (`docs/decisoes.md`)

## Auditoria run-4 — onda 2: reservas e dinheiro (`docs/decisoes.md`)

- **Início do aluguel:** a reivindicação usa o status exato lido (`free` ou `reserved`); `reserved` exige a reserva do próprio cliente ainda `active`/`handover` na mesma transação; `convert()` devolve a contagem e o início aborta se 0. Rollback e varredura só voltam a `reserved` com a reserva do cliente ainda aberta (senão `free`), e nunca sobrescrevem um status que não seja `rented`.
- **Pix de rua:** `reserveForPix` estende a reserva só se ela ainda está `active` e no prazo (senão `409`) e pede a liberação da caução anterior quando a troca; recusa da reserva libera a caução Pix recém-criada. O job `depot-reservations-orphan-deposits` também libera caução de rua (`deposit:<cliente>:<chave>`) `held`/`awaiting_pix` 10 min após o prazo do Pix; o filtro fica no SQL (`NOT EXISTS` em `Rental`, `Reservation` `active`/`handover`, `RentalStart`, `DepositRelease`) e só reserva aberta protege a caução.
- **Reserva:** a expiração pelo TTL do Redis (e o passe de vencidas da varredura) só encerra com `expiresAt <= agora`; reserva estendida tem a chave regravada. `vehicle.status_changed` `free` só quando a moto saiu de fato de `reserved`.
- **`Idempotency-Key`:** 8 a 128 caracteres em `[A-Za-z0-9_-]` (`400 validation-error`); UUID v4 passa. Caução devolvida por `holdDeposit` que pertence a reserva aberta de outro fluxo → `409 deposit-in-use`.
- **Estorno:** `PaymentRefund.gatewayRefundedBefore` (migração `20261103130000_payment_refund_baseline`) guarda o total estornado no gateway antes da chamada; a reconciliação exige `before + amountCents` (o `providerPaymentId` pode ser compartilhado). Pedido antigo sem linha de base só confia no total do gateway se nenhum outro `Payment` compartilha o id.
- **Pacotes de minutos:** no plano por minuto sem assinatura, os minutos da carteira abatem a linha `time` (linha `minute_package`, negativa) antes da carteira em reais, com lançamento `minute_package` (minutos negativos, `rentalId`) na transação do fechamento.
- **Estorno de recarga:** tira o crédito da carteira uma vez por incremento (`TopUp.reversedCents`, migração `20261103131000_top_up_reversed_cents`): `top_up` negativo de `min(incremento, saldo)` ou os minutos proporcionais do pacote; falta de saldo → `payment.needs-review` (`top_up_refund_exceeds_balance`). Estorno do admin de recarga cujo crédito já foi gasto além do saldo → `409`. Só estorno confirmado conta (pedidos `claimed`/`pending` são descontados). Estorno total confirmado do aluguel devolve os minutos de pacote consumidos (parcial não devolve).
