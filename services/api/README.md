# API Volti (`services/api`)

NestJS 10 + Prisma 5 + PostgreSQL 16/PostGIS + Redis 7. Implementa as 182 operações de `packages/contracts/openapi.yaml` e o WebSocket de `packages/contracts/realtime.md` (Socket.IO, namespace `/realtime`).

## Como rodar localmente

```bash
cp .env.example .env                    # na raiz do monorepo
cp .env.example services/api/.env       # o Prisma CLI lê o .env da pasta do pacote
pnpm install
pnpm dev:deps                           # postgres, redis, mosquitto, minio (a API cria os buckets ao subir)
pnpm --filter api prisma migrate deploy # aplica prisma/migrations
pnpm --filter api prisma db seed        # São Paulo: 60 motos (Urbana/Sport/Touring), zonas, preços, estações, baterias, usuários dev
pnpm --filter api dev                   # prisma generate + tsc e sobe em http://localhost:3000
```

Ou tudo em containers: `docker compose up -d --build api` (sobe sem `.env`, com padrões de dev; porta do host em `API_PORT`, padrão 3000) (o container aplica as migrações com `RUN_MIGRATIONS=true`; `RUN_SEED=true` roda o seed).

> **Migrações:** aplique com `migrate deploy`. Use `migrate dev` só para criar migração nova, revisando o SQL gerado. A migração inicial tem índices GIST e parciais e `CHECK` escritos à mão, e o setup do e2e confere que existem. Para checar drift, rode `prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script`: o resultado deve ser uma migração vazia.

> `tsx`/esbuild não emite metadados de decorators; por isso o `dev` usa `tsc`. O seed roda com `tsx` (não usa DI).

### Tokens de desenvolvimento (`AUTH_MODE=dev`)

```bash
curl -X POST localhost:3000/dev/token -H 'content-type: application/json' \
  -d '{"sub":"dev-cliente-aprovado","email":"cliente.aprovado@volti.dev","groups":[],"pool":"customer"}'
curl -X POST localhost:3000/dev/token -H 'content-type: application/json' \
  -d '{"sub":"dev-admin","email":"admin@volti.dev","groups":["admin"],"pool":"staff"}'
```

Usuários do seed: `dev-admin`, `dev-operacao`, `dev-financeiro`, `dev-suporte`, `dev-campo` (staff) e `dev-cliente-aprovado` / `dev-cliente-pendente` (clientes). As motos `VLT-0001`…`VLT-0006` ficam dentro das zonas de devolução. O seed do contrato v2 (`prisma/seed-v2.ts`) acrescenta o catálogo de exemplo (`prisma/seed-catalog.ts`): Volti Urbana — urbana com cesto (79/min), Volti Sport — esportiva compacta de 2 lugares (89/min) e Volti Touring — touring com baú (99/min), todos autopropelidos de até 1000 W e 32 km/h, com descrição curta e desbloqueio do plano; as fotos de exemplo (de terceiros, só dev — nunca no git) são baixadas no seed direto para `catalogo/catalog/<slug>.<ext>` no MinIO (só HTTPS e host público em cada salto, até 3 redirecionamentos, até 5 MB, assinatura JPEG/PNG/WebP conferida), e sem rede o modelo fica sem foto (o app mostra o ícone); as motos alternam os modelos pelo código (`VLT-0001` Urbana, `VLT-0002` Sport, `VLT-0003` Touring…), então o lote do galpão tem 6/7/7; 5 estações de troca, odômetro/horas e revisões variadas (em dia, próxima, vencida), uma bateria por moto, 6 baterias na van do `dev-campo`, o cupom `BEMVINDO10` e, para o `dev-cliente-aprovado`, chave Pix (e-mail) e código de indicação `APROVADO7K`. O seed do galpão (`prisma/seed-depot.ts`, idempotente) cria o "Galpão Volti — Pinheiros" (Rua dos Pinheiros, 870; seg–sex 07:00–20:00, sáb 08:00–18:00, dom fechado) e vincula a ele só o lote `VLT-0011`…`VLT-0030` (`DEPOT_CODES`, sem as motos que os e2e usam no fluxo de rua), quando livres, nas coordenadas do galpão; motos fora do lote que apontem para o galpão são desvinculadas e voltam às coordenadas do seed (um banco semeado antes do fix se repara rodando o seed de novo).

## Estrutura

- `src/ports/` — interfaces fixas: `IotGateway`, `RentalBillingPort`, `InsurancePort` (plano mestre), `ObjectStorage`, `QueueBus`, `KycProvider`, `PushNotifier`, `AuthVerifier`, `StaffDirectory` e `CustomerIdentityDirectory` (Cognito; local = no-op), `ReverseGeocoder` (contrato v2: endereço da moto).
- `src/adapters/` — implementações local/aws escolhidas por variável (`AUTH_MODE`, `STORAGE_MODE`, `QUEUE_MODE`, `KYC_PROVIDER`, `PUSH_MODE`). Valor desconhecido em qualquer `*_MODE` recusa subir.
- `src/modules/iot` — **Task 4** (ver "IoT" abaixo).
- `src/modules/payments`, `insurance`, `wallet` — **Task 5** (`docs/pagamentos.md`): `RentalBillingService` (caução por pré-autorização ou Pix, liquidação com captura parcial, inadimplência) sobre `PaymentProvider` (`PAYMENT_PROVIDER=fake|mercadopago`), webhooks do Mercado Pago validados, enfileirados e deduplicados (`ProcessedWebhook`), carteira em ledger somente inserção, `InsuranceService` com `MockInsuranceProvider` e repasse, recibo em PDF no bucket de relatórios e NFS-e (`MockInvoiceIssuer`). No fake, o cartão precisa ser cadastrado antes de alugar (`POST /payments/cards` com `cardToken: tok_visa_4242`); o Pix se confirma sozinho após `FAKE_PIX_AUTOCONFIRM_SECONDS`.
- `src/common/` — enums compartilhados, erros RFC 7807 (`ProblemException` → `type: https://api.volti.com.br/problems/<slug>`), idempotência (`@Idempotent`), paginação por cursor, logger JSON sem dados pessoais.
- Eventos internos: `src/common/events.ts` (os do plano mestre + os próprios da API, ver `docs/decisoes.md`).
- Jobs (`JOBS_ENABLED`): expiração de reservas (TTL do Redis + varredura), retentativa de encerramento `ending`, `rental.updated` a cada 30 s, "você está bem?" (60 s), limpeza diária de `TrackPoint` expirado.

## IoT (`src/modules/iot`, Task 4)

| Variável | Valores | Efeito |
|---|---|---|
| `IOT_MODE` | `local` (padrão), `aws`, `stub` | `LocalMqttIotGateway` (Mosquitto em `MQTT_URL`, com o servidor emulando o serviço de shadow), `AwsIotGateway` (IoT Data Plane em `IOT_ENDPOINT`; telemetria pela fila SQS `telemetria`) ou o `StubIotGateway` (confirma na hora; padrão dos e2e do fluxo de aluguel) |
| `GEOFENCE_MODE` | `local` (padrão), `aws` | ENTER/EXIT pelo PostGIS; `aws` também sincroniza a geofence collection e o tracker do Amazon Location (`LOCATION_GEOFENCE_COLLECTION`, `LOCATION_TRACKER_NAME`) |
| `IOT_CONFIRM_WAIT_MS` | `3000` | quanto a chamada de comando espera o `reported` antes de responder `in_progress` |
| `IOT_COMMAND_TIMEOUT_MS` | `30000` | sem `reported` → `failed`/`timeout` (o lock tem 120 s) |
| `IOT_OFFLINE_AFTER_MS` | `180000` | sem notícia → `iot.connectivity` offline |
| `IOT_RECONNECT_GRACE_MS` | `10000` | depois de qualquer reconexão, nenhuma amostra de velocidade (telemetria, reported, polling do shadow) vale para travar neste intervalo (fila offline do MQTT esvaziada). Reconexão = presença `connected` (só `local`), primeira mensagem depois de offline, primeira amostra do processo ou lacuna (`IOT_RECONNECT_GAP_MS`) |
| `IOT_QUEUE_LAG_MS` | `5000` | telemetria com atraso de fila `(chegada − chegada anterior) − (timestamp − timestamp anterior)` maior que isto saiu da fila offline → reconexão (a amostra cai na graça); independe da cadência e do desvio do relógio do rastreador |
| `IOT_RECONNECT_GAP_MS` | `15000` | lacuna entre mensagens do rastreador (qualquer canal, hora de chegada) que conta como reconexão, nos dois modos; com a moto parada/travada vale `max(isto, 150000)`. No `aws` é o único detector de quedas mais curtas que `IOT_OFFLINE_AFTER_MS` (a presença vai para o EventBridge) |
| `OUT_OF_AREA_LOCK_MINUTES` | `5` | bloqueio seguro depois de sair da área de operação |
| `TRACK_RETENTION_DAYS` | `90` | `TrackPoint.expiresAt` |

- Bloqueio seguro (`safe-lock.service.ts`): rampa `min(atual,15) → 8 → 3 → 0`, um degrau 2 s depois do `reported`; `travada: true` só com velocidade reportada < 3 km/h; 120 s → `did_not_stop`.
- Telemetria (`telemetry.service.ts`): emite `iot.telemetry`/`iot.device-event`/`iot.connectivity`; grava `TrackPoint` só com aluguel `active`/`paused`/`ending`.
- Cercas (`geofence/`): `reduced_speed` ajusta o limite (comando de sistema com AuditLog); saída da `operation` com aluguel → alerta e bloqueio em 5 min.
- Contrato MQTT: `packages/contracts/mqtt.md`; firmware: `docs/firmware-bloqueio-seguro.md`; ADR: `docs/adr-rastreador.md`.
- Provisionar rastreador: `pnpm --filter api exec tsx scripts/provision-tracker.ts --vehicle VLT-0061 --thing moto-0061 --imei 860000000000061 --mode aws|local`.
- Simulador: `services/iot-sim` (`docker compose --profile sim up -d iot-sim`).
- Teste de integração: `pnpm --filter api test:e2e -- test/iot` (Mosquitto + Postgres/Redis do compose; sobe o simulador sozinho).

Fix round 1 (`docs/decisoes.md`): pausa/retomada só com confirmação do gateway (`503 gateway-unavailable`), ciclo de vida das assinaturas (`canceled`/`expired` pelo job), regra única da moto fixa com período vigente (`common/fixed-vehicle.ts`), posição oculta de motos em uso por outros clientes (`locationHidden`), HMAC do CPF contra fraude. `test/migration-v2.e2e-spec.ts` aplica as migrações v2 sobre um banco com as anteriores e dados legados (assinaturas duplicadas).

Retirada em galpão — modelo de dados (Task 2 do plano `2026-10-22-volti-galpao`): `Depot`, `Handover` (saída `pickup` com aceite do cliente; chegada `return_depot`), `Vehicle.depotId` (disponível no galpão = `free` com `depotId`), campos de retirada em `Reservation` (`depotId`, `pickupMode`, `pickupAt`, `planCode`, `coverage`, `depositMethod`, `cardId`, `couponCode`, `reminderSentAt`; todos nulos na reserva de rua), `VehicleStatus.awaiting_pickup` e `ReservationStatus.handover`. Migrações `20261023085900_galpao_enums` (só `ALTER TYPE … ADD VALUE`, separada porque o Postgres não usa valor novo de enum na mesma transação) e `20261023090000_galpao` (aditiva) e `20261023091000_galpao_pickup_unique` (troca a unicidade da saída por índice parcial; nome do galpão único). SQL à mão: `Handover_one_open_return_per_rental` (uma chegada não cancelada por aluguel), `Handover_one_open_pickup_per_reservation` (uma saída `pending_customer`/`accepted` por reserva; disputada ou cancelada libera refazer), `CHECK` `Handover_type_reference` (`pickup` exige `reservationId`, `return_depot` exige `rentalId`), `Reservation_one_active_per_customer`/`_vehicle` passam a valer para `active` e `handover`, `CHECK` `Handover_battery_pct_range` e `Depot_windows_range`. `test/migration-galpao.e2e-spec.ts` aplica as migrações do galpão sobre um banco com as anteriores e uma moto/reserva no formato antigo.

Retirada em galpão — moto fora da rua (Task 7): moto do galpão (com `depotId`, ou que saiu por uma entrega `pickup` aceita para o aluguel) encerrada em ponto verde (`POST /rentals/{id}/end` ou encerramento forçado) termina em `awaiting_pickup` e ganha uma tarefa `collect` (prioridade `medium`, destino = posição da moto), criada sob `pg_advisory_xact_lock` por moto e só se não houver `collect` aberta. Moto de rua (sem `depotId`) continua voltando a `free`. `RentalEndService.finalize(..., { returnTo: 'depot' })` é o caminho da devolução no galpão (Task 6): não cria recolhimento. Concluir a `collect` com `depotId` (`POST /field-tasks/{id}/complete`) põe a moto em `free` (ou no `vehicleStatus` enviado) com esse `depotId` e as coordenadas do galpão; sem `depotId` numa moto `awaiting_pickup` → `422`. `GET /vehicles/nearby` do cliente exclui motos com `depotId` e `awaiting_pickup` (staff vê todas); `POST /rentals` de cliente para moto com `depotId` ou `awaiting_pickup` → `409 vehicle-unavailable` (`isDepotLocked` em `rental-start.service.ts`, onde a Task 6 põe o bypass `fromHandover`). Rastreador que volta online mantém `awaiting_pickup`. O export LGPD inclui `depotReservations` (sem `pickupCode`) e `handovers` (fotos só como chaves). `test/galpao-ponto-verde.e2e-spec.ts` cobre o ciclo.

Retirada em galpão — entrega (Task 6): `HandoversService`. **Saída** (`POST /handovers`, `type: pickup`, `admin`/`operacao`/`campo`): `verifyPickupCode` (adulterado/vencido → `404`), reserva de galpão `active` (ou `handover` sem saída aberta, depois de uma disputa) com a moto `reserved`, `depotId` enviado igual ao da reserva (`422`); numa transação a reserva vai a `handover` e nasce a entrega `pending_customer` (segunda saída aberta → `409`, índice parcial); evento `handover.pending`. **Aceite** (`POST /handovers/{id}/accept`, cliente dono; outro → `404`; `Idempotency-Key` obrigatória): já aceita → devolve o mesmo aluguel; fora de `pending_customer` → `422 handover-not-pending`; caução da reserva não retida ou em liberação → `422 deposit-not-held`; trava por entrega (`IdempotencyStore`, escopo `handover-accept`; concorrente → `409`, tenta de novo e converge). Delega a `RentalStartService.start(customer, { vehicleId, planCode, coverage, depositMethod, cardId, couponCode, depositId }, 'handover:<id>', { fromHandover })`: o bypass de `isDepotLocked` só vale com a moto `reserved` pela reserva do próprio cliente em `handover`; o aluguel, a conversão da reserva e a entrega `accepted` com `rentalId` gravam na mesma transação (a moto guarda o `depotId` de origem enquanto alugada), depois do desbloqueio confirmado (entrega disputada no meio → `422` e compensação normal: moto volta a `reserved`, lock de sistema, apólice cancelada). Com `fromHandover` a caução nunca é liberada pelo `start()` nem pela varredura de inícios órfãos (é da reserva, que segue `handover`). Erro do `start()` → `lastError` com o slug (só recusa de pagamento vira `422 payment-declined`; nada é gravado se a moto já está `rented` por um `start()` desta mesma entrega) e `handover.updated`; a entrega segue pendente. **Disputa** (`/dispute`): `disputed` + conversa de suporte (`SupportService.createConversation`, uma nova tentativa; falhando, AuditLog `handover.dispute_ticket_failed`); moto `reserved`, reserva `handover`. **Cancelamento** (`/cancel`, `admin`/`operacao`/`campo`): saída `pending_customer`/`disputed` → `canceled` (AuditLog `handover.cancel`); reserva volta a `active` no prazo (novo `pickupCode`, nova saída) ou vira `expired` com caução liberada e moto `free` no galpão; aceita ou com aceite em andamento → `409`. **Chegada** (`type: return_depot`, `rentalId` e `depotId` obrigatórios): entrega `accepted`, `RentalEndService.endAtDepot(actor, rentalId, { depotId, targetStatus })` (lock seguro com rampa, sem esperar a confirmação; o fechamento grava `free` — ou `maintenance` se algum item veio `ok: false` — e o `depotId` num único `updateMany`, sem janela `free` sem galpão; offline: `statusBeforeOffline`), `collect` aberta cancelada; chegada não cancelada já existente → `200` com ela (fila offline), terminando o que faltou. `GET /handovers/{id}` (dono da reserva ou do aluguel; staff), `GET /handovers` (staff, cursor, filtros `status`/`depotId`/`type`), `photoUrls` assinadas por 24 h (bucket `fotos-devolucao`, prefixo `handovers/`), `operatorFirstName` só o primeiro nome. WebSocket: salas `customer:{id}` (cliente) e `depot:{id}` (staff `admin`/`operacao`/`campo`, todos os galpões existentes ao conectar). A troca de moto em aluguel (`POST /rentals/{id}/swap`) recusa moto com `depotId` ou `awaiting_pickup` (`409 vehicle-unavailable`).

Retirada em galpão — reserva (Task 5): `POST /reservations` com `depotId` vai para `DepotReservationsService` (sem `depotId`, o fluxo de rua de sempre). Exige `Idempotency-Key` (`400` sem a chave; o contrato a marca opcional porque o OpenAPI não expressa a condição), `pickupMode`, `planCode`, `coverage` e `depositMethod`. Valida galpão ativo (`422 depot-inactive`), horário (`depot-rules.ts`: `422 pickup-outside-hours`/`pickup-too-far-ahead`; "agora" com o galpão fechado também vira `pickup-outside-hours`), KYC/bloqueio/inadimplência/termos, aluguel aberto (`409 rental-already-active`), reserva aberta `active|handover` (`409 reservation-open`), moto `free` do mesmo galpão e não fixa de outro plano (`409 vehicle-unavailable`). Bloqueia a caução pelo mesmo `RentalBillingPort` do aluguel (chave `deposit:<cliente>:reservation:<Idempotency-Key>`; cartão pré-autorizado no `cardId` ou no padrão, recusa → `422 payment-declined`; Pix devolve `deposit.pix`) e separa a moto com `updateMany` condicional (`free` + mesmo `depotId` → `reserved`); quem perde a corrida tem a caução liberada e recebe `409`. `expiresAt` vem de `pickupExpiry`. A resposta e `GET /reservations/current` (que agora traz `active` ou `handover`, com `handoverId`) levam o `pickupCode` (`pickup-code.ts`: `v1.<reservationId>.<expEpoch>.<HMAC-SHA256 base64url>`, sem dado pessoal), só para o dono e só enquanto `active`. `DELETE /reservations/{id}` libera a caução e a moto; em `handover` → `409 reservation-in-handover`. A varredura/TTL de reservas também expira as de galpão. Job `depot-reservations-remind` (1 min): push "Sua retirada vence às HH:MM" (fuso do galpão) uma vez por reserva (`reminderSentAt`). A reserva de rua recusa moto com `depotId` (`409 vehicle-unavailable`). Fix round 1: caução Pix que vence sem pagamento (`awaiting_pix → failed`) emite `deposit.failed` e a reserva expira (a varredura também expira reservas de galpão com caução `failed` ou Pix vencido); `cancel` que perde a corrida responde 409 (nunca 204 sem cancelar); a varredura busca as vencidas primeiro (`expiresAt <= agora`, 500 mais antigas) e regrava as chaves do Redis num passe separado; job `depot-reservations-orphan-deposits` (5 min) libera caução de reserva sem reserva nem aluguel após 10 min; `cardId` só com `depositMethod: card`; sem lembrete quando a reserva inteira dura 30 min ou menos. `PICKUP_CODE_SECRET` (obrigatório em produção; em dev, segredo local). `test/depot-reservations.e2e-spec.ts` cobre 400 sem chave, cartão/Pix, repetição idempotente, corrida, moto fixa, handover e o fluxo de rua.

Fix round 2: assinatura `canceled`/`expired` nunca reabre. A cobrança tardia é estornada pelo gateway (`PaymentRefund`, chave `subscription-late-refund:<paymentId>`). O cancelamento no gateway de assinatura expirada ou de conta excluída fica pendente (`gatewayCancelPendingAt`) e é refeito pelo job `subscriptions-gateway-cancel-retry` (5 min). O odômetro usa compare-and-set atômico no Redis (`RedisStore.hcas`, testado contra o Redis real em `test/usage-tracker-redis.e2e-spec.ts`).

## Troca de bateria na estação via QR (`src/modules/station-swaps`, spec `2026-10-22-volti-troca-bateria-qr`)

Cliente com aluguel em andamento escaneia o QR fixo da estação e troca a bateria sozinho. `POST /swap-stations/{id}/swaps` (cliente, `Idempotency-Key` obrigatória) valida, nesta ordem: QR (`404 station-not-found`), aluguel do próprio cliente `active`/`paused` (`409 rental-not-active`), uma troca aberta por aluguel (`409 swap-open`, também pelo índice parcial `StationSwap_one_open_per_rental`), estação ativa, aberta (`open24h` ou `openingHours` interpretável no fuso de São Paulo; texto ilegível libera) e com carregada livre (`availableBatteries` menos as trocas em andamento) (`422 station-unavailable`), celular a ≤ 50 m (`422 too-far`) e moto parada — mesma regra do bloqueio seguro: velocidade 0 fresca, moto travada e online ou aluguel pausado; desconhecida = em movimento (`422 vehicle-moving`; `IotGateway.knownSpeedKmh`). `GET /swap-stations/{id}/swaps/{swapId}` (dono + `admin`/`operacao`/`suporte`), `POST .../cancel` (dono, só em `opening_slot`/`awaiting_return`; depois `422 swap-not-cancelable`), `GET /swap-stations/{id}/swaps` (staff, cursor, filtro `status`, com `customerId` e `distanceM`).

- **Estados:** `opening_slot` → `awaiting_return` (`slot_opened`) → `returned` (`battery_returned`) → `releasing` (`slot_closed`; só aqui a API manda `release_battery`) → `completed` (`battery_released`). Vaga fechada sem devolução → `canceled`. Eventos repetidos/fora de ordem/de outra estação são ignorados. WebSocket `station_swap.updated { swapId, status }` na sala `customer:{id}`.
- **Prazos:** 3 min por etapa (`expiresAt`, `STATION_SWAP_STEP_TIMEOUT_MS`); job `station-swap-timeouts` (15 s, `JOBS_ENABLED`): sem resposta da estação → `failed/station_timeout`; sem devolução → `canceled/return_timeout`; devolvida sem liberar → `failed/release_timeout` + alerta `command_failed` (alta) para a operação. Liberação atrasada depois desse prazo ainda completa a troca (o cliente recebeu a bateria).
- **Estoque:** devolvida → `Battery` `charging` na estação com série e carga lidas (também numa troca já cancelada, uma vez por troca); liberada → `availableBatteries − 1` (nunca negativo), bateria `in_vehicle` na moto com +1 ciclo (mesma regra da troca do operador), `Vehicle.batterySerial`/`batteryPct` atualizados. A API sugere a carregada (`serialHint`: `in_station`, ≥ 90 %, mais carregada) e grava a que a estação informar.
- **Taxa:** congelada na criação (`feeCents`): 0 nos planos `day`/`weekly`/`monthly`; nos `minute`/`hour`, a taxa de sistema `battery_swap_fee` (padrão 500, criada pela migração; o admin edita em `PUT /pricing/fees/{id}`, não apaga). Cobrada só no fechamento: `RentalEndService` soma uma linha `battery_swap_fee` por troca `completed` com taxa na mesma liquidação.
- **LGPD/logs:** a posição do celular só é usada na validação; a troca guarda a distância (só staff vê). Logs só com ids. O export LGPD traz `stationSwaps`.
- **Porta da estação** (`src/ports/station-gateway.port.ts`), pelo mesmo `IOT_MODE`: `stub` (`StubStationGateway`, avança sozinha a cada `STATION_STUB_STEP_MS`, padrão 1500 ms; `setAuto(false)` e `emit` nos testes), `local` (`MqttStationGateway`, Mosquitto + `services/station-sim`) e `aws` (`AwsStationGateway`: `Publish` no IoT Data Plane; eventos da fila SQS `estacoes`, `SQS_QUEUE_ESTACOES_URL`). Tópicos `estacoes/station-{id}/comandos|eventos`.
- **QR da estação:** `SwapStation.stationCode` = `vst1.<id>.<HMAC-SHA256 truncado, base64url>` assinado com `STATION_QR_SECRET` (obrigatório em produção; em dev, segredo local). A API confere a assinatura **e** a igualdade com o banco (revogar = trocar o segredo e rodar a emissão de novo). O código nunca sai em `SwapStation`. O seed emite para todas as estações (`prisma/seed-station-codes.ts`) e imprime `station_qr_codes`.

## Segurança e LGPD (correções do QA, `docs/relatorio-qa.md`)

| Variável | Padrão | Efeito |
|---|---|---|
| `CORS_ORIGINS` | vazio | origens aceitas (vírgulas), HTTP e Socket.IO, sem credenciais; vazio = só `localhost` fora de produção, nenhuma em produção |
| `TRUST_PROXY` | vazio | saltos de proxy confiáveis (`1` atrás do ALB); vazio = ignora `X-Forwarded-For` |
| `TERMS_CURRENT_VERSION` | vazio | versão dos termos exigida em `POST /rentals` (vazio = basta ter aceitado) |

- Produção (`NODE_ENV=production`) recusa `AUTH_MODE=dev` e `MERCADOPAGO_WEBHOOK_SECRET=CHANGE_ME`.
- Autorização: grupos do staff = cadastro ∩ token, lidos a cada requisição (`PATCH /staff/{id}` vale na hora e é espelhado no pool pelo `StaffDirectory`). Cognito: só access token; staff casado pelo `sub`.
- Exclusão de conta: identidade excluída no pool de clientes, `cognitoSub` vira `deleted:<sha256(sub)>` e o token antigo recebe 401; trajetos, posição de início, fotos de devolução e documentos de KYC são apagados.
- Consentimento de localização revogado durante o aluguel: o trajeto para de ser gravado na hora.
- `POST /rentals`: moto offline ou desbloqueio não confirmado → `409 vehicle-offline`, sem aluguel nem cobrança; o relógio começa no desbloqueio confirmado.
- Rate limit no Redis (compartilhado entre instâncias); cabeçalhos `helmet`; exportação LGPD com `Cache-Control: no-store`; link do recibo assinado na leitura (15 min).

## Regras que nunca mudam

- Nenhum `speedLimitKmh` fora de 0..32 é aceito (DTO → 400 `speed-limit-out-of-range`; serviço de comandos revalida; `CHECK` no banco).
- Encerrar só em zona `return`, com foto e travamento confirmado; liquidação uma única vez por aluguel.
- Localização só durante o aluguel; trajetos expiram em 90 dias; exportação/exclusão LGPD só do próprio titular.
