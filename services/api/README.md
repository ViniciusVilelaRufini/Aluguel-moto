# API Volti (`services/api`)

NestJS 10 + Prisma 5 + PostgreSQL 16/PostGIS + Redis 7. Implementa as 188 operações de `packages/contracts/openapi.yaml` e o WebSocket de `packages/contracts/realtime.md` (Socket.IO, namespace `/realtime`).

## Como rodar localmente

```bash
cp .env.example .env                    # na raiz do monorepo
cp .env.example services/api/.env       # o Prisma CLI lê o .env da pasta do pacote
pnpm install
pnpm dev:deps                           # postgres, redis, mosquitto, minio (a API cria os buckets ao subir)
pnpm --filter api prisma migrate deploy # aplica prisma/migrations
pnpm --filter api prisma db seed        # São Paulo: 60 motos (Urbana/Sport/Touring), zonas, preços, estações, baterias, usuários dev
pnpm --filter api dev                   # prisma generate + tsc e sobe em http://localhost:3000
```

Ou tudo em containers: `docker compose up -d --build api` (sobe sem `.env`, com padrões de dev; porta do host em `API_PORT`, padrão 3000) (o container aplica as migrações com `RUN_MIGRATIONS=true`; `RUN_SEED=true` roda o seed).

> **Migrações:** aplique com `migrate deploy`. Use `migrate dev` só para criar migração nova, revisando o SQL gerado. A migração inicial tem índices GIST e parciais e `CHECK` escritos à mão, e o setup do e2e confere que existem. Para checar drift, rode `prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script`: o resultado deve ser uma migração vazia.

> `tsx`/esbuild não emite metadados de decorators; por isso o `dev` usa `tsc`. O seed roda com `tsx` (não usa DI).

### Tokens de desenvolvimento (`AUTH_MODE=dev`)

```bash
curl -X POST localhost:3000/dev/token -H 'content-type: application/json' \
  -d '{"sub":"dev-cliente-aprovado","email":"cliente.aprovado@volti.dev","groups":[],"pool":"customer"}'
curl -X POST localhost:3000/dev/token -H 'content-type: application/json' \
  -d '{"sub":"dev-admin","email":"admin@volti.dev","groups":["admin"],"pool":"staff"}'
```

Usuários do seed: `dev-admin`, `dev-operacao`, `dev-financeiro`, `dev-suporte`, `dev-campo` (staff) e `dev-cliente-aprovado` / `dev-cliente-pendente` (clientes). As motos `VLT-0001`…`VLT-0006` ficam dentro das zonas de devolução. O seed do contrato v2 (`prisma/seed-v2.ts`) acrescenta o catálogo de exemplo (`prisma/seed-catalog.ts`): Volti Urbana — urbana com cesto (79/min), Volti Sport — esportiva compacta de 2 lugares (89/min) e Volti Touring — touring com baú (99/min), todos autopropelidos de até 1000 W e 32 km/h, com descrição curta e desbloqueio do plano; as fotos de exemplo (de terceiros, só dev — nunca no git) são baixadas no seed direto para `catalogo/catalog/<slug>.<ext>` no MinIO (só HTTPS e host público em cada salto, até 3 redirecionamentos, até 5 MB, assinatura JPEG/PNG/WebP conferida), e sem rede o modelo fica sem foto (o app mostra o ícone); as motos alternam os modelos pelo código (`VLT-0001` Urbana, `VLT-0002` Sport, `VLT-0003` Touring…), então o lote do galpão tem 6/7/7; 5 estações de troca, odômetro/horas e revisões variadas (em dia, próxima, vencida), uma bateria por moto, 6 baterias na van do `dev-campo`, o cupom `BEMVINDO10` e, para o `dev-cliente-aprovado`, chave Pix (e-mail) e código de indicação `APROVADO7K`. O seed do galpão (`prisma/seed-depot.ts`, idempotente) cria o "Galpão Volti — Pinheiros" (Rua dos Pinheiros, 870; seg–sex 07:00–20:00, sáb 08:00–18:00, dom fechado) e vincula a ele só o lote `VLT-0011`…`VLT-0030` (`DEPOT_CODES`, sem as motos que os e2e usam no fluxo de rua), quando livres, nas coordenadas do galpão; motos fora do lote que apontem para o galpão são desvinculadas e voltam às coordenadas do seed (um banco semeado antes do fix se repara rodando o seed de novo).

## Estrutura

- `src/ports/` — interfaces fixas: `IotGateway`, `RentalBillingPort`, `InsurancePort` (plano mestre), `ObjectStorage`, `QueueBus`, `KycProvider`, `PushNotifier`, `AuthVerifier`, `StaffDirectory` e `CustomerIdentityDirectory` (Cognito; local = no-op), `ReverseGeocoder` (contrato v2: endereço da moto).
- `src/adapters/` — implementações local/aws escolhidas por variável (`AUTH_MODE`, `STORAGE_MODE`, `QUEUE_MODE`, `KYC_PROVIDER`, `PUSH_MODE`). Valor desconhecido em qualquer `*_MODE` recusa subir.
- `src/modules/iot` — **Task 4** (ver "IoT" abaixo).
- `src/modules/payments`, `insurance`, `wallet` — **Task 5** (`docs/pagamentos.md`): `RentalBillingService` (caução por pré-autorização ou Pix, liquidação com captura parcial, inadimplência) sobre `PaymentProvider` (`PAYMENT_PROVIDER=fake|mercadopago`), webhooks do Mercado Pago validados, enfileirados e deduplicados (`ProcessedWebhook`), carteira em ledger somente inserção, `InsuranceService` com `MockInsuranceProvider` e repasse, recibo em PDF no bucket de relatórios e NFS-e (`MockInvoiceIssuer`). No fake, o cartão precisa ser cadastrado antes de alugar (`POST /payments/cards` com `cardToken: tok_visa_4242`); o Pix se confirma sozinho após `FAKE_PIX_AUTOCONFIRM_SECONDS`.
- `src/common/` — enums compartilhados, erros RFC 7807 (`ProblemException` → `type: https://api.volti.com.br/problems/<slug>`), idempotência (`@Idempotent`), paginação por cursor, logger JSON sem dados pessoais.
- Eventos internos: `src/common/events.ts` (os do plano mestre + os próprios da API, ver `docs/decisoes.md`).
- Jobs (`JOBS_ENABLED`): expiração de reservas (TTL do Redis + varredura), retentativa de encerramento `ending`, `rental.updated` a cada 30 s, "você está bem?" (60 s), limpeza diária de `TrackPoint` expirado.

## IoT (`src/modules/iot`, Task 4)

| Variável | Valores | Efeito |
|---|---|---|
| `IOT_MODE` | `local` (padrão), `aws`, `stub` | `LocalMqttIotGateway` (Mosquitto em `MQTT_URL`, com o servidor emulando o serviço de shadow), `AwsIotGateway` (IoT Data Plane em `IOT_ENDPOINT`; telemetria pela fila SQS `telemetria`) ou o `StubIotGateway` (confirma na hora; padrão dos e2e do fluxo de aluguel) |
| `GEOFENCE_MODE` | `local` (padrão), `aws` | ENTER/EXIT pelo PostGIS; `aws` também sincroniza a geofence collection e o tracker do Amazon Location (`LOCATION_GEOFENCE_COLLECTION`, `LOCATION_TRACKER_NAME`) |
| `IOT_CONFIRM_WAIT_MS` | `3000` | quanto a chamada de comando espera o `reported` antes de responder `in_progress` |
| `IOT_COMMAND_TIMEOUT_MS` | `30000` | sem `reported` → `failed`/`timeout` (o lock tem 120 s) |
| `IOT_OFFLINE_AFTER_MS` | `180000` | sem notícia → `iot.connectivity` offline |
| `IOT_RECONNECT_GRACE_MS` | `10000` | depois de qualquer reconexão, nenhuma amostra de velocidade (telemetria, reported, polling do shadow) vale para travar neste intervalo (fila offline do MQTT esvaziada). Reconexão = presença `connected` (só `local`), primeira mensagem depois de offline, primeira amostra do processo ou lacuna (`IOT_RECONNECT_GAP_MS`) |
| `IOT_QUEUE_LAG_MS` | `5000` | telemetria com atraso de fila `(chegada − chegada anterior) − (timestamp − timestamp anterior)` maior que isto saiu da fila offline → reconexão (a amostra cai na graça); independe da cadência e do desvio do relógio do rastreador |
| `IOT_RECONNECT_GAP_MS` | `15000` | lacuna entre mensagens do rastreador (qualquer canal, hora de chegada) que conta como reconexão, nos dois modos; com a moto parada/travada vale `max(isto, 150000)`. No `aws` é o único detector de quedas mais curtas que `IOT_OFFLINE_AFTER_MS` (a presença vai para o EventBridge) |
| `OUT_OF_AREA_LOCK_MINUTES` | `5` | bloqueio seguro depois de sair da área de operação |
| `TRACK_RETENTION_DAYS` | `90` | `TrackPoint.expiresAt` |

- Bloqueio seguro (`safe-lock.service.ts`): rampa `min(atual,15) → 8 → 3 → 0`, um degrau 2 s depois do `reported`; `travada: true` só com velocidade reportada < 3 km/h; 120 s → `did_not_stop`.
- Telemetria (`telemetry.service.ts`): emite `iot.telemetry`/`iot.device-event`/`iot.connectivity`; grava `TrackPoint` só com aluguel `active`/`paused`/`ending`.
- Cercas (`geofence/`): `reduced_speed` ajusta o limite (comando de sistema com AuditLog); saída da `operation` com aluguel → alerta e bloqueio em 5 min.
- Contrato MQTT: `packages/contracts/mqtt.md`; firmware: `docs/firmware-bloqueio-seguro.md`; ADR: `docs/adr-rastreador.md`.
- Provisionar rastreador: `pnpm --filter api exec tsx scripts/provision-tracker.ts --vehicle VLT-0061 --thing moto-0061 --imei 860000000000061 --mode aws|local`.
- Simulador: `services/iot-sim` (`docker compose --profile sim up -d iot-sim`).
- Teste de integração: `pnpm --filter api test:e2e -- test/iot` (Mosquitto + Postgres/Redis do compose; sobe o simulador sozinho).

Fix round 1 (`docs/decisoes.md`): pausa/retomada só com confirmação do gateway (`503 gateway-unavailable`), ciclo de vida das assinaturas (`canceled`/`expired` pelo job), regra única da moto fixa com período vigente (`common/fixed-vehicle.ts`), posição oculta de motos em uso por outros clientes (`locationHidden`), HMAC do CPF contra fraude. `test/migration-v2.e2e-spec.ts` aplica as migrações v2 sobre um banco com as anteriores e dados legados (assinaturas duplicadas).

Retirada em galpão — modelo de dados (Task 2 do plano `2026-10-22-volti-galpao`): `Depot`, `Handover` (saída `pickup` com aceite do cliente; chegada `return_depot`), `Vehicle.depotId` (disponível no galpão = `free` com `depotId`), campos de retirada em `Reservation` (`depotId`, `pickupMode`, `pickupAt`, `planCode`, `coverage`, `depositMethod`, `cardId`, `couponCode`, `reminderSentAt`; todos nulos na reserva de rua), `VehicleStatus.awaiting_pickup` e `ReservationStatus.handover`. Migrações `20261023085900_galpao_enums` (só `ALTER TYPE … ADD VALUE`, separada porque o Postgres não usa valor novo de enum na mesma transação) e `20261023090000_galpao` (aditiva) e `20261023091000_galpao_pickup_unique` (troca a unicidade da saída por índice parcial; nome do galpão único). SQL à mão: `Handover_one_open_return_per_rental` (uma chegada não cancelada por aluguel), `Handover_one_open_pickup_per_reservation` (uma saída `pending_customer`/`accepted` por reserva; disputada ou cancelada libera refazer), `CHECK` `Handover_type_reference` (`pickup` exige `reservationId`, `return_depot` exige `rentalId`), `Reservation_one_active_per_customer`/`_vehicle` passam a valer para `active` e `handover`, `CHECK` `Handover_battery_pct_range` e `Depot_windows_range`. `test/migration-galpao.e2e-spec.ts` aplica as migrações do galpão sobre um banco com as anteriores e uma moto/reserva no formato antigo.

`online` da moto (staff, `GET /vehicles`, `GET /vehicles/{id}`, `GET /depots/{id}/vehicles`): derivado em `vehicles.mapper.ts` (`trackerOnline`) — `true` só se a coluna `online` está ligada **e** o `lastSeenAt` (última telemetria; o overlay do Redis o deixa fresco) está dentro da janela `IOT_OFFLINE_AFTER_MS` (padrão 180 s, a mesma da vigia de inatividade). A coluna nasce `true`; sem isso, moto que nunca teve rastreador conectado aparecia online. O `status` (`offline`) continua vindo dos eventos de conectividade.

Retirada em galpão — moto fora da rua (Task 7): moto do galpão (com `depotId`, ou que saiu por uma entrega `pickup` aceita para o aluguel) encerrada em ponto verde (`POST /rentals/{id}/end` ou encerramento forçado) termina em `awaiting_pickup` e ganha uma tarefa `collect` (prioridade `medium`, destino = posição da moto), criada sob `pg_advisory_xact_lock` por moto e só se não houver `collect` aberta. Moto de rua (sem `depotId`) continua voltando a `free`. `RentalEndService.finalize(..., { returnTo: 'depot' })` é o caminho da devolução no galpão (Task 6): não cria recolhimento. Concluir a `collect` com `depotId` (`POST /field-tasks/{id}/complete`) põe a moto em `free` (ou no `vehicleStatus` enviado) com esse `depotId` e as coordenadas do galpão; sem `depotId` numa moto `awaiting_pickup` → `422`. `GET /vehicles/nearby` do cliente exclui motos com `depotId` e `awaiting_pickup` (staff vê todas); `POST /rentals` de cliente para moto com `depotId` ou `awaiting_pickup` → `409 vehicle-unavailable` (`isDepotLocked` em `rental-start.service.ts`, onde a Task 6 põe o bypass `fromHandover`). Rastreador que volta online mantém `awaiting_pickup`. O export LGPD inclui `depotReservations` (sem `pickupCode`) e `handovers` (fotos só como chaves). `test/galpao-ponto-verde.e2e-spec.ts` cobre o ciclo.

Retirada em galpão — entrega (Task 6): `HandoversService`. **Saída** (`POST /handovers`, `type: pickup`, `admin`/`operacao`/`campo`): `verifyPickupCode` (adulterado/vencido → `404`), reserva de galpão `active` (ou `handover` sem saída aberta, depois de uma disputa) com a moto `reserved`, `depotId` enviado igual ao da reserva (`422`); numa transação a reserva vai a `handover` e nasce a entrega `pending_customer` (segunda saída aberta → `409`, índice parcial); evento `handover.pending`. **Aceite** (`POST /handovers/{id}/accept`, cliente dono; outro → `404`; `Idempotency-Key` obrigatória): já aceita → devolve o mesmo aluguel; fora de `pending_customer` → `422 handover-not-pending`; caução da reserva não retida ou em liberação → `422 deposit-not-held`; trava por entrega (`IdempotencyStore`, escopo `handover-accept`; concorrente → `409`, tenta de novo e converge). Delega a `RentalStartService.start(customer, { vehicleId, planCode, coverage, depositMethod, cardId, couponCode, depositId }, 'handover:<id>', { fromHandover })`: o bypass de `isDepotLocked` só vale com a moto `reserved` pela reserva do próprio cliente em `handover`; o aluguel, a conversão da reserva e a entrega `accepted` com `rentalId` gravam na mesma transação (a moto guarda o `depotId` de origem enquanto alugada), depois do desbloqueio confirmado (entrega disputada no meio → `422` e compensação normal: moto volta a `reserved`, lock de sistema, apólice cancelada). Com `fromHandover` a caução nunca é liberada pelo `start()` nem pela varredura de inícios órfãos (é da reserva, que segue `handover`). Erro do `start()` → `lastError` com o slug (só recusa de pagamento vira `422 payment-declined`; nada é gravado se a moto já está `rented` por um `start()` desta mesma entrega) e `handover.updated`; a entrega segue pendente. **Disputa** (`/dispute`): `disputed` + conversa de suporte (`SupportService.createConversation`, uma nova tentativa; falhando, AuditLog `handover.dispute_ticket_failed`); moto `reserved`, reserva `handover`. **Cancelamento** (`/cancel`, `admin`/`operacao`/`campo`): saída `pending_customer`/`disputed` → `canceled` (AuditLog `handover.cancel`); reserva volta a `active` no prazo (novo `pickupCode`, nova saída) ou vira `expired` com caução liberada e moto `free` no galpão; aceita ou com aceite em andamento → `409`. **Chegada** (`type: return_depot`, `rentalId` e `depotId` obrigatórios): entrega `accepted`, `RentalEndService.endAtDepot(actor, rentalId, { depotId, targetStatus, lat, lng })` (lock seguro com rampa, sem esperar a confirmação; o fechamento grava `free` — ou `maintenance` se algum item veio `ok: false` —, o `depotId` e a posição do galpão (`lat`/`lng`, como na conclusão da `collect`) num único `updateMany`, sem janela `free` sem galpão; offline: `statusBeforeOffline`, também com a posição do galpão), `collect` aberta cancelada; chegada não cancelada já existente → `200` com ela (fila offline), terminando o que faltou. `GET /handovers/{id}` (dono da reserva ou do aluguel; staff), `GET /handovers` (staff, cursor, filtros `status`/`depotId`/`type`), `photoUrls` assinadas por 24 h (bucket `fotos-devolucao`, prefixo `handovers/`), `operatorFirstName` só o primeiro nome. WebSocket: salas `customer:{id}` (cliente) e `depot:{id}` (staff `admin`/`operacao`/`campo`, todos os galpões existentes ao conectar). A troca de moto em aluguel (`POST /rentals/{id}/swap`) recusa moto com `depotId` ou `awaiting_pickup` (`409 vehicle-unavailable`).

Retirada em galpão — reserva (Task 5): `POST /reservations` com `depotId` vai para `DepotReservationsService` (sem `depotId`, o fluxo de rua de sempre). Exige `Idempotency-Key` (`400` sem a chave; o contrato a marca opcional porque o OpenAPI não expressa a condição), `pickupMode`, `planCode`, `coverage` e `depositMethod`. Valida galpão ativo (`422 depot-inactive`), horário (`depot-rules.ts`: `422 pickup-outside-hours`/`pickup-too-far-ahead`; "agora" com o galpão fechado também vira `pickup-outside-hours`), KYC/bloqueio/inadimplência/termos, aluguel aberto (`409 rental-already-active`), reserva aberta `active|handover` (`409 reservation-open`), moto `free` do mesmo galpão e não fixa de outro plano (`409 vehicle-unavailable`). Bloqueia a caução pelo mesmo `RentalBillingPort` do aluguel (chave `deposit:<cliente>:reservation:<Idempotency-Key>`; cartão pré-autorizado no `cardId` ou no padrão, recusa → `422 payment-declined`; Pix devolve `deposit.pix`) e separa a moto com `updateMany` condicional (`free` + mesmo `depotId` → `reserved`); quem perde a corrida tem a caução liberada e recebe `409`. `expiresAt` vem de `pickupExpiry`. Fix round 2: assinatura `canceled`/`expired` nunca reabre. A cobrança tardia é estornada pelo gateway (`PaymentRefund`, chave `subscription-late-refund:<paymentId>`). ## Troca de bateria na estação via QR (`src/modules/station-swaps`, spec `2026-10-22-volti-troca-bateria-qr`)

Cliente com aluguel em andamento escaneia o QR fixo da estação e troca a bateria sozinho. `POST /swap-stations/{id}/swaps` (cliente, `Idempotency-Key` obrigatória) valida, nesta ordem: QR (`404 station-not-found`), aluguel do próprio cliente `active`/`paused` (`409 rental-not-active`), uma troca aberta por aluguel (`409 swap-open`, também pelo índice parcial `StationSwap_one_open_per_rental`), estação ativa, aberta (`open24h` ou `openingHours` interpretável no fuso de São Paulo; texto ilegível libera) e com carregada livre (`availableBatteries` menos as trocas em andamento) (`422 station-unavailable`), celular a ≤ 50 m (`422 too-far`) e moto parada — mesma regra do bloqueio seguro: velocidade 0 fresca, moto travada e online ou aluguel pausado; desconhecida = em movimento (`422 vehicle-moving`; `IotGateway.knownSpeedKmh`). `GET /swap-stations/{id}/swaps/{swapId}` (dono + `admin`/`operacao`/`suporte`), `POST .../cancel` (dono, só em `opening_slot`/`awaiting_return`; depois `422 swap-not-cancelable`), `GET /swap-stations/{id}/swaps` (staff, cursor, filtro `status`, com `customerId` e `distanceM`).

- **Estados:** `opening_slot` → `awaiting_return` (`slot_opened`) → `returned` (`battery_returned`) → `releasing` (`slot_closed`; só aqui a API manda `release_battery`) → `completed` (`battery_released`). Vaga fechada sem devolução → `canceled`. Eventos repetidos/fora de ordem/de outra estação são ignorados. Eventos, cancelamento e prazo de uma troca passam por uma fila por troca (um de cada vez, CAS no status). WebSocket `station_swap.updated { swapId, status }` na sala `customer:{id}`.
- **Última bateria (fix 1, C1):** a checagem de estoque e a inserção correm na mesma transação com `SELECT … FOR UPDATE` na estação; contam as trocas em andamento e as `failed/release_timeout` dos últimos 30 min (a estação ainda pode liberar atrasada). Duas requisições pela última carregada → `201` + `422 station-unavailable`.
- **Moto parada (fix 1, I3):** velocidade 0 fresca ou moto travada e online — o aluguel `paused` sozinho não basta (pausado com velocidade desconhecida → `422 vehicle-moving`).
- **Prazos:** 3 min por etapa (`expiresAt`, `STATION_SWAP_STEP_TIMEOUT_MS`); job `station-swap-timeouts` (15 s, `JOBS_ENABLED`): sem resposta da estação → `failed/station_timeout`; sem devolução → `canceled/return_timeout`; devolvida sem liberar → `failed/release_timeout` + alerta `command_failed` (alta) para a operação. Liberação atrasada depois desse prazo ainda completa a troca (o cliente recebeu a bateria).
- **Aviso à estação (fix 1, I2):** cancelamento pelo cliente e todo prazo vencido mandam `abort_swap { swapId, slotNumber? }`; a estação fecha a vaga e confirma com `slot_closed` (ignorado pela API numa troca encerrada). Devolução que chega depois de `canceled_by_customer`, `return_timeout` ou `station_timeout` vale como devolução: a bateria entra no estoque, a troca volta para `releasing` (com a estação travada, mesma conta da criação) e a estação libera uma carregada; sem carregada → `failed/no_battery_after_return` + alerta.
- **Devolução atrasada com o aluguel fechado (fix 2, I-1/M-4):** antes de voltar a `releasing`, a transação trava a estação e o aluguel (`FOR UPDATE`, sempre nessa ordem) e confere aluguel `active`/`paused` e nenhuma outra troca aberta; se falhar, a devolução fica registrada e a troca vira `failed/return_after_close` + alerta (nunca P2002: um P2002 inesperado cai numa transação nova que grava o mesmo resultado, para o evento não virar mensagem envenenada no grupo FIFO). Devolução numa troca encerrada por outro motivo só entra no estoque + alerta.
- **Encerramento pelo staff (fix 2, M-2):** encerramento forçado e chegada no galpão fecham as trocas abertas sem devolução (`canceled/rental_force_ended` + `abort_swap`); com a devolução registrada a liberação termina, mas `Vehicle.batterySerial` e o registro da bateria não mudam com o aluguel já fechado (alerta para conferir).
- **Criação × encerramento (fix 2, M-3):** a criação relê o status do aluguel e a troca aberta com a linha do aluguel travada (depois do lock da estação); o encerramento pelo cliente trava a mesma linha antes de conferir a troca aberta e passar a `ending`.
- **Série divergente (fix 1, M1):** bateria devolvida ou liberada que consta `in_vehicle` em outra moto nunca é desvinculada: troca `failed/serial_mismatch` + alerta. Devolvida diferente da registrada na moto, ou liberada fora do estoque da estação → alerta (só ids), a troca segue.
- **Aluguel durante a troca (fix 1, I1/I7):** `GET /rentals/current` traz `currentStationSwap` (troca aberta, visão do cliente). Com troca aberta, `POST /rentals/{id}/end` e `POST /rentals/{id}/swap` → `409 swap-open`; o encerramento forçado pelo staff continua permitido.
- **Estoque:** devolvida → `Battery` `charging` na estação com série e carga lidas (uma vez por troca); liberada → `availableBatteries − 1` (nunca negativo), bateria `in_vehicle` na moto com +1 ciclo (mesma regra da troca do operador), `Vehicle.batterySerial`/`batteryPct` atualizados. A API sugere a carregada (`serialHint`: `in_station`, ≥ 90 %, mais carregada) e grava a que a estação informar.
- **Taxa:** congelada na criação (`feeCents`): 0 nos planos `day`/`weekly`/`monthly`; nos `minute`/`hour`, a taxa de sistema `battery_swap_fee` (padrão 500, criada pela migração; o admin edita em `PUT /pricing/fees/{id}`, não apaga). Cobrada só no fechamento: `RentalEndService` soma uma linha `battery_swap_fee` por troca `completed` com taxa na mesma liquidação.
- **LGPD/logs:** a posição do celular só é usada na validação; a troca guarda a distância (só staff vê). Logs só com ids. O export LGPD traz `stationSwaps`.
- **Thing da estação (Task 12 das lacunas):** `SwapStation.thingName` (único, `station-<uuid>`; a criação pelo painel grava `station-{id}` quando não informada; nulo nas linhas antigas = `station-{id}`). Os comandos vão para a thing do cadastro e os eventos são atribuídos à estação com esse `thingName` (ou, sem nenhuma, à `station-{id}` cujo cadastro não aponta para outro armário); thing desconhecida → evento ignorado (log `station_event_unknown_thing`). A criação de troca relê `active` sob o lock da estação, então uma desativação pelo painel nunca deixa nascer troca numa estação inativa; eventos de trocas já em curso (inclusive devolução atrasada) continuam sendo processados numa estação inativa.
- **Porta da estação** (`src/ports/station-gateway.port.ts`), pelo mesmo `IOT_MODE`: `stub` (`StubStationGateway`, avança sozinha a cada `STATION_STUB_STEP_MS`, padrão 1500 ms; `setAuto(false)` e `emit` nos testes; **recusado em produção**: com `NODE_ENV=production`, `IOT_MODE=stub` não sobe), `local` (`MqttStationGateway`, Mosquitto + `services/station-sim`) e `aws` (`AwsStationGateway`: `Publish` no IoT Data Plane; eventos da fila SQS `estacoes`, `SQS_QUEUE_ESTACOES_URL`). Tópicos `estacoes/station-{id}/comandos|eventos`.
- **Modo aws — fila FIFO (fix 1, I4):** `SQS_QUEUE_ESTACOES_URL` tem de terminar em `.fifo` (`MessageGroupId` = `thing` da estação); com outra fila (ou sem ela) a API não sobe. O `SqsQueueBus` lê o `MessageGroupId` e, quando o handler de uma mensagem falha, não processa nem apaga o resto do mesmo grupo naquele lote (as mensagens voltam na ordem depois do visibility timeout); os outros grupos seguem.
- **QR da estação:** `SwapStation.stationCode` = `vst1.<id>.<HMAC-SHA256 truncado, base64url>` assinado com `STATION_QR_SECRET` (obrigatório em produção; em dev, segredo local). A API confere a assinatura **e** a igualdade com o banco. O código nunca sai em `SwapStation`. **Emissão (fix 1, I6), fora do seed:** script de operação `pnpm --filter api stations:qr` (emite para as estações sem código; `--reissue` regrava todos com o segredo atual — revogação depois de trocar o `STATION_QR_SECRET`; `--station=<id>` filtra). Em produção: `node dist/cli/issue-station-qr.js [--reissue]` numa task avulsa do ECS com `DATABASE_URL` e `STATION_QR_SECRET`. Admin e operação leem o QR de uma estação em `GET /swap-stations/{id}/qr` (o mesmo código do script; emite na hora se faltar; AuditLog `swap_station.qr_read`, sem o código) — o painel desenha e imprime o QR a partir dele.

## Ciclo de vida das baterias no galpão (`src/modules/batteries`, `docs/decisoes.md` 2026-10-24)

Status: `in_vehicle`, `in_van`, `charging` (no galpão `depotId`, ou na estação `stationId` depois da troca por QR), `charged` (carregada e pronta no galpão, carga 100 até sair), `in_station`, `defective` (fora de uso) e `retired` (baixa).

| Rota | Grupos | Regra |
|---|---|---|
| `POST /batteries` | admin, operacao | cadastra por série no galpão ativo, `charging` (carga informada, padrão 0) ou `charged` (100); série duplicada → `409`; galpão inexistente → `404`, inativo → `422 depot-inactive` |
| `POST /batteries/{id}/mark-charged` | admin, operacao, campo | `charging → charged` (carga 100, mesmo galpão); carregando numa estação (sem galpão) → `in_station` e `availableBatteries + 1`; outro status → `409` |
| `POST /batteries/{id}/report-defect` | admin, operacao, campo | `{ reason }`; de `charging`/`charged`/`in_van`/`in_station` → `defective`; instalada numa moto → `409` (retire antes). Na estação, carregada sai do `availableBatteries`; na van, `holderId` é mantido (quem está com ela) e ela some do estoque da van |
| `POST /batteries/{id}/retire` | admin, operacao | `{ reason? }`; de `defective`/`charging`/`charged` → `retired` (limpa galpão, van e estação) |
| `GET /batteries/{id}/movements` | admin, operacao, suporte, campo | cursor, mais recente primeiro |
| `GET /batteries?depotId=&status=` | admin, operacao, campo | `statusCounts` com os 7 status (filtros `depotId`/`holderId`/`q`, sem `status` nem paginação) |

- **Van:** `load` recusa `defective`/`retired` (`409`), tira a bateria do galpão (`depotId` nulo) e mantém a carga conhecida; séries que ainda estavam `charging` voltam em `loadedChargingSerials`. `unload` sem `stationId` grava `charging` com o `depotId` do corpo, ou do único galpão ativo; com mais de um (ou nenhum) → `422 depot-required`.
- **Movimentações (`BatteryMovement`):** uma linha por transição, na mesma transação — cadastro (`fromStatus` nulo), van (carregar/descarregar no galpão ou na estação), mark-charged, defeito, baixa, troca na tarefa de campo (retirada → van, instalada → moto, outra registrada na moto → `charging`) e troca na estação por QR (devolvida → `charging` na estação, liberada → moto; ator = cliente). Galpão/estação/moto da linha: o destino, senão a origem. A troca na tarefa também recusa instalar, ou registrar como retirada, bateria `defective`/`retired` (`409`).
- **Alerta `battery_stock_low`:** `Depot.minChargedBatteries` (nulo ou 0 = sem alerta; `PATCH /depots/{id}`; só staff vê no `Depot`). Quando uma bateria sai de `charged` e o galpão fica abaixo do mínimo, `BatteryStockService` abre um alerta `medium` com `depotId` — um não resolvido por galpão (checagem + índice parcial `Alert_one_open_stock_low_per_depot`; `P2002` numa corrida é ignorado). Na própria API de baterias (van, defeito, baixa) a checagem roda depois do commit e é best-effort (falha só vira log `battery_stock_check_failed`, a operação responde normalmente); nas trocas (tarefa e estação), pelo evento interno `battery.charged-stock-decreased`.
- **Migrações:** `20261024130000_baterias_galpao_enums` (só `ADD VALUE`) e `20261024131000_baterias_galpao` (colunas anuláveis `Battery.depotId`, `Depot.minChargedBatteries`, `Alert.depotId`, tabela `BatteryMovement` com FK em cascata — a API nunca apaga bateria, só os testes —, índice parcial). Linhas antigas em `charging` sem galpão continuam válidas.
- **Testes:** `batteries.service.spec.ts`, `battery-movements.spec.ts`, `battery-stock.service.spec.ts`, movimentações em `field-tasks.service.spec.ts` e `station-swaps.service.spec.ts`, `contract-schemas-baterias.spec.ts`; e2e `test/baterias-galpao.e2e-spec.ts` (cadastrar → van → galpão → mark-charged → van → defeito → baixa, histórico paginado, alerta deduplicado, grupos).

| `TRUST_PROXY` | vazio | saltos de proxy confiáveis (`1` atrás do ALB); vazio = ignora `X-Forwarded-For` |

- Autorização: grupos do staff = cadastro ∩ token, lidos a cada requisição (`PATCH /staff/{id}` vale na hora e é espelhado no pool pelo `StaffDirectory`). Cognito: só access token; staff casado pelo `sub`. No primeiro login de um `sub` sem cadastro, o e-mail verificado vem do pool (`StaffDirectory.verifiedEmail`, `AdminGetUser`) e liga o convite criado pelo `POST /staff` (M7 da revisão final).
- Dívida em aberto (inadimplência, flag `delinquent` e bloqueio da exclusão LGPD): regra única em `src/modules/payments/open-debt.ts` (aluguel e assinatura `failed` sem `debtSettledAt`, mais cobrança ainda em curso no gateway). Exclusão de conta com mensalidade recusada não quitada → `409 account-deletion-blocked`.

Task 14: também mensagens e anexos do chat, fotos das entregas, ocorrências e sinistros encerrados (em andamento ficam até o desfecho; o job diário limpa depois) e o cliente com os cartões no gateway (`ProviderCustomerDeletion`, job `lgpd-gateway-deletion-retry` a cada 5 min, até 10 tentativas). - Rate limit no Redis (compartilhado entre instâncias); cabeçalhos `helmet`; exportação LGPD com `Cache-Control: no-store`; link do recibo assinado na leitura (15 min).

## Inadimplência e alerta de pagamento (`src/modules/payments/delinquency.service.ts`, Task 14)

- Dívida = pagamento de aluguel/assinatura `failed` sem `debtSettledAt`; saldo devedor (`outstandingCents`) = valor − caução capturada como garantia.
- `POST /payments/{id}/retry` (cliente): cobra o saldo no cartão (na hora) ou por Pix (quita no webhook) num `Payment` `debt_settlement`. `409 debt-in-collection` enquanto a cobrança automática ainda corre: aluguel com a liquidação retentando no cartão, ou assinatura **desta dívida** `past_due` (o gateway retenta a recorrência) ou com o cancelamento no gateway pendente. `503 gateway-unavailable` quando o resultado de uma tentativa não pode ser conferido (ela fica `pending`).
- Quitação manual: bloqueada só pela liquidação de aluguel em retentativa ou pela assinatura ligada a uma das dívidas. `onLatePaid` (Pix pago depois de virar `failed`) é idempotente por pagamento.
- `POST /customers/{id}/delinquency/clear` (admin/financeiro): quitação manual com motivo no AuditLog.
- `payment.needs-review` vira o alerta `payment_needs_review` (um aberto por pagamento). Financeiro vê só esses alertas; operação não os vê.
- `GET /customers/{id}` traz `walletBalanceCents` e `debtCents` para admin/financeiro.
- CSV dos relatórios em pt-BR (cabeçalhos, R$ com vírgula, datas de São Paulo); a receita tem `walletCents` (pago com carteira).

## Correções da varredura E2E na AWS (Task 30)

- **Cartão padrão:** `PUT /payments/cards/{id}/default` (idempotente). O primeiro cartão (ou o primeiro com a conta sem padrão) vira padrão; remover o padrão promove o ativo mais recente. Sem `cardId`, toda cobrança usa `resolveCustomerCard` (padrão → ativo mais recente). Caução no cartão (reserva de galpão e `POST /rentals`) e assinatura sem nenhum cartão ativo → `422 card-required`, checado antes de criar a caução (`payments/card-required.ts`). Migração de dados `20261025200000_default_card_backfill`.
- **Exclusão de conta:** também recusada (`409 account-deletion-blocked`, mensagem do que fazer) com reserva aberta (`active`/`handover`) ou caução `held`/`awaiting_pix`.
- **Aceite com a moto sem conexão:** `409 vehicle-offline` com texto próprio do aceite (a caução continua retida; nada cobrado).
- **Nome da equipe:** o staff criado no primeiro login fica sem nome; para o cliente sai o primeiro nome cadastrado ou "Equipe Volti" (`common/staff-display-name.ts`). Migração de dados `20261025201000_staff_name_not_from_email`.
- **E-mail do cliente:** `CustomerIdentityDirectory.contactInfo` (aws: `AdminGetUser` no pool de clientes, só atributos verificados; local: `null`) preenche e-mail/telefone no primeiro acesso e completa quem ficou com `@sem-email.volti.invalid` (no máximo uma consulta a cada 10 min por cliente e instância).
- **Anexos do chat:** `SupportMessage.attachmentUrls` (só staff; GET pré-assinado de 15 min; só chaves `support/<authorId>/…`).

## Fechamento sem cartão (R2-01, lacunas Task 16)

- Ordem no fechamento: **carteira → caução → cartão salvo → dívida**. A carteira é debitada (`rental_charge`) na transação que fecha o aluguel (cliente travado com `FOR UPDATE`), aparece como linha `wallet` no `breakdown` e só o restante vai para a liquidação; carteira cobrindo tudo → pagamento `method: wallet` e caução liberada. A caução Pix abate e devolve só o saldo; sem cartão, o restante vira dívida (`outstandingCents`), paga no app por Pix (`POST /payments/{id}/retry`).
- O `Payment` do aluguel registra o bruto, com a parte da carteira em `walletCents` (NFS-e e PDF pelo bruto); o estorno devolve primeiro a parte do gateway e depois credita a carteira (`refund` no ledger).
- Dívida em aberto (ou flag `delinquent`) → reservas recusadas com `409 payment-pending` ("Pague o valor pendente para alugar de novo."); `POST /rentals` segue `403 customer-delinquent`.
- `GET /rentals/{id}/receipt`: `paymentStatus` (`paid`/`pending`/`processing`), `paymentId`, `depositUsedCents`, `depositReleasedCents`, `amountDueCents`; `pdfUrl` só pago. Quitada a dívida (Pix, cartão, webhook tardio ou manual), o recibo (PDF + NFS-e) é emitido.
- Testes: bloco "Task 16" em `rental-billing.service.spec.ts` (cada ordem de liquidação), `rental-end.service.spec.ts` (carteira no fechamento), `delinquency.service.spec.ts`, `eligibility.spec.ts`, reservas; e2e `test/lacunas-t16.e2e-spec.ts` (QA sem cartão → dívida → 409 → Pix pago → recibo com PDF; carteira total; carteira parcial; caução + cartão) e o caso 14 do contrato.

## Várias instâncias e integrações (lacunas T5, `docs/decisoes.md` 2026-10-24)

A API roda com 2–10 tasks no ECS. Tudo o que precisa ser único ou compartilhado passa pelo Redis (`REDIS_URL`; com `memory`, o `MemoryRedisStore` faz o mesmo papel num processo só):

- **Tempo real:** Socket.IO com `@socket.io/redis-adapter` (`src/modules/realtime/redis-io.adapter.ts`, ligado no `main.ts`). Evento processado numa instância chega aos sockets de todas.
- **Bloqueio seguro:** estado da rampa em `RedisSafeLockStore` (`src/modules/iot/safe-lock.store.ts`, sem TTL, índice em hash), lock por moto e varredura de 1 s (`IotRuntime`). Falha fechada: sem estado, nada é publicado; `travada: true` só com velocidade fresca < 3 km/h; órfã do índice e prazo de 120 s → comandos `failed`, hold e a rampa continua gradual (nunca limite 0 de uma vez). Com rampa ativa, só reduções. Redis fora: lock usa rampa local em memória, migrada para o Redis quando ele volta.
- **Redis fora do ar:** limites de zona continuam valendo (cercas degradam para o estado local; reduções de limite sempre aceitas; só subidas recusadas).
- **Cercas e "fora da área":** estado por moto e prazo no Redis, sob lock da moto (`geofence.service.ts`); varredura de prazos a cada 15 s; só uma instância dispara.
- **Jobs:** `@ExclusiveJob(nome, ttl)` (`src/common/job-lock.ts`) — cada rodada de `@Interval`/`@Cron` roda numa instância só.
- **Alertas:** a fila `alertas` aceita `CreateAlertInput` ou o evento cru do rastreador (`{ thingName, tipo, timestamp }`).
- **Presença:** `{ thingName, presence }` da fila de telemetria → `inbound.presence`.
- **Push:** `PUSH_MODE=fcm` + `FCM_SERVICE_ACCOUNT_JSON` (firebase-admin); `log` em dev. `data.type` segue o roteamento do app (`reservation.reminder`, `kyc`, …).
- **Produção recusa:** `PAYMENT_PROVIDER=fake` (salvo `ALLOW_FAKE_PAYMENTS=true`, só o dev da infra), `ALLOW_TEST_HANDOVER=true` sem `ALLOW_FAKE_PAYMENTS=true` (e, em qualquer ambiente, sem `PAYMENT_PROVIDER=fake`), `PUBLIC_SHARE_BASE_URL` ausente ou sem https, `PUSH_MODE=fcm` sem credencial válida.
- **Cognito:** `COGNITO_STAFF_CLIENT_IDS` (painel + app do operador).
- **SOS:** `GET /public/location-shares/{token}` (JSON, sem auth, 30/min por IP) e `GET /share/{token}` (página). Só posição + horário, com link válido, aluguel aberto e consentimento.
- **Estações:** `slot_closed` sem devolução espera 5 s (`STATION_SLOT_CLOSED_GRACE_MS`) por um `battery_returned` atrasado antes de cancelar.

Testes: `safe-lock.multi-instance.spec.ts`, `safe-lock.redis-store.spec.ts` (suítes do bloqueio seguro de novo com o estado serializado no "Redis"), `geofence.multi-instance.spec.ts`, `live-state.multi-instance.spec.ts`, `job-lock.spec.ts`; e2e `realtime-multi-instance`, `multi-instance-redis` (Redis real) e `location-share-public`.
